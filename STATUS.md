# Статус проекта

Актуальный статус по каждому шагу плана — в [docs/dev-tree.md](docs/dev-tree.md)
(дерево этапов/шагов со ссылками на код). Формулы и алгоритмы, на которых
строится конвейер — в [docs/math-model.md](docs/math-model.md).

**Коротко на сейчас:** Этап 0 — кодовая часть шагов 0.2 (генератор/валидатор
тестовых IFC), 0.4 (пересчёт координат МСК-59 и калибровка высот), 0.6
(аудит полноты OSM), 0.7 (Docker Compose для разработки), 0.8 (словарь
данных) сделана и протестирована. Шаги 0.1, 0.3, 0.5 требуют действий вне
кода и не могут быть закрыты AI-сессией.

Этап 1 в работе:
- Шаг 1.1 (импорт OSM в PostGIS) — флекс-стиль osm2pgsql на 8 таблиц, журнал
  источников, скрипты импорта/обновления и запрос выборки в радиусе реально
  проверены локальным `osm2pgsql`+PostGIS.
- Шаг 1.2 (рельеф) — репроекция в МСК-59, пересчёт высот, COG-конвертация,
  слияние источников с плавным переходом (формула §2.4 math-model.md) и
  индекс покрытия в PostGIS + `get_dem(bbox)` реально проверены (rasterio/GDAL,
  локальный PostGIS, 26 тестов). Рабочая сетка задачи — 1 м
  (`RELIEF_PIXEL_SIZE_M`, было 10 м): TIN участка и рельеф тайла сэмплируют
  именно её, крупный шаг обрезал бы точность точечных источников (топосъёмка)
  ещё до TIN. На предельном радиусе 3 км (6400×6400 пикс.) шаг целиком
  измерен реальным прогоном ~15 с — укладывается в критерий «3 км ≤ 15 мин».
- Шаг 1.3 (API и очередь задач) — FastAPI (`POST /jobs`, `GET /jobs/{id}`,
  `GET /models/{id}/files`, `GET /models/{id}/download`, `GET /viewer/`),
  модель задач в PostGIS, реальная очередь Celery+Redis (проверена настоящим
  воркером в отдельном процессе), пайплайн из шести шагов
  (select_osm/prepare_relief/select_and_normalize/assemble_ifc/
  convert_to_glb/package_outputs — последний добавлен Шагом 2.10) поверх
  Шагов 1.1/1.2/1.4-1.9/2.10. Оба критерия приёмки шага
  подтверждены тестами: 10 параллельных задач не мешают друг другу, упавший
  шаг перезапускается без пересчёта предыдущих; сквозной прогон всего
  пайплайна (реальный `osm2pgsql` → рельеф → выборка → `site.ifc` → `site.glb`)
  тоже проверен (`test_full_happy_path_creates_downloadable_files`).
- Шаг 1.4 (выборка и нормализация данных) — выборка объектов в буфере,
  репроекция в МСК-59, обрезка кругом и перевод в локальные координаты,
  нормализация тегов по словарю данных (confidence факт/умолчание) и
  сохранение в GeoPackage реально проверены (61 тест, план требовал 20+ на
  нормализацию — сделано 35).
- Шаг 1.5 (TIN участка) — фон по методу квадратных призм (сетка 1 м, было
  25 м) с многоструктурным 2D-сглаживанием, врезка дорог/воды/зданий,
  критерий «≤0.1 м» подтверждён на точной синтетической плоскости (13
  тестов). Подключён как часть шага `assemble_ifc`. Реальным прогоном
  измерено ограничение масштаба: несвязанный `Delaunay` на шаге 1 м тянет
  до ~800 м (500 м — ~14 с/~1,5 ГБ), на 1,5 км реальный прогон уже уходил
  за 12 ГБ — выше этого `build_site_tin` теперь явно отказывает вместо
  падения по памяти; для радиуса больше ~800 м — тайловый путь Шага 2.1.
- Шаг 1.6 (здания) — экструзия по высоте (`height` → `levels×3+1` → дефолт
  по типу), низ = min рельефа по контуру, исправление геометрии (19 тестов).
- Шаг 1.7 (дороги/вода/рельсы/деревья) — ленты по ширине из тега/класса,
  балласт ж/д, деревья одиночные+массивы по плотности; вода — контур
  сглажен методом Чайкина (концы русла не трогаются), уровень — сглаженный
  профиль вдоль длинной оси для вытянутых водоёмов/рек (не единый `min` по
  контуру — важно для полномасштабных объектов на склоне, `docs/water.md`)
  (21 тест на точную геометрию/сглаживание/уровень).
- Шаг 1.8 (сборка IFC) — `IfcProject`→`IfcSite` с геопривязкой, каждый слой
  Шагов 1.5-1.7 → меш (`mapbox_earcut`, здания — замкнутая призма, проверено
  объёмом по теореме о дивергенции) + класс IFC + Pset, `IfcRoad` нативно в
  IFC4X3/прокси в IFC4 (приём совместимости Шага 0.2), реестр `GlobalId` в
  PostGIS, валидация `ifcopenshell.validate` — 0 замечаний. Дорожное покрытие
  обязательно выше рельефа, не вровень (`PAVEMENT_CLEARANCE_M`, найден и
  исправлен попутный баг — абсолютный Z=0 за пределами TIN вместо отметки
  ближайшей вершины, `docs/pavement.md`) (29 тестов).
- Шаг 1.9 (веб-просмотр) — IFC → GLB (`ifcopenshell.geom.iterator` по
  реальной модели, узлы с GlobalId/классом/Pset в `extras`, сгруппированы по
  слоям), статический вьюер на three.js (облёт, слои, дерево объектов,
  панель свойств по клику), ссылка на модель из журнала задачи
  (`viewer_url` в `/models/{id}/files`). Проверено в настоящем headless
  Chromium (Playwright): модель грузится <1 с (критерий — ≤10 с), дерево/
  свойства реально работают (11 тестов). XKT не реализован — только GLB
  (обоснование в `ifc/to_glb.py`); проверка «на телефоне» не делалась — нет
  устройства.
- Шаг 1.10 (тесты и приёмка этапа 1) — конвейер целиком прогнан на 3
  синтетических профилях участка (центр/спальный район/частный сектор,
  реальные `osm2pgsql`+PostGIS+Redis), время каждого шага снято из журнала
  задачи, «расхождение с OSM ≤0,5 м» проверено сравнением по Хаусдорфу
  экспортированного контура и нормализованных координат Шага 1.4 (0 м на
  опорном прогоне). Протокол — `docs/stage1-acceptance.md`. Проверка
  BIM-специалистом в Renga/Pilot-BIM (п. 3-4 шага) — вне возможностей
  AI-сессии, нужен реальный пилот (0.1) и человек с этим ПО.

Всем шагам не хватает реальных данных (выгрузка OSM/TessaDEM по краю,
выбранный пилот — Шаг 0.1) и/или живого MinIO (нет демона Docker в этой
среде) для проверки количественных критериев на настоящих объёмах и в
полном проде; Шагам 1.5-1.10 дополнительно — визуальной приёмки BIM-
специалистом в Renga/Pilot-BIM (нужен человек с этим ПО). Подробности по
каждому шагу — `docs/dev-tree.md`.

**Этап 1 (кодовая часть) закрыт.** Все шаги 1.1-1.10 реализованы и
протестированы в объёме, доступном без внешних сторон; официальное
закрытие этапа (п. 9 плана — решение РП) ждёт того, что не может сделать
AI-сессия: выбор пилота (0.1) и приёмку BIM-специалистом в Renga/Pilot-BIM.

Этап 2 начат:
- Шаг 2.1 (кольца LOD и тайловый кеш) — кольца LOD2/LOD1/LOD0 по границам
  плана, тайлы 250×250 м в мировых координатах МСК-59 (не локальных
  координатах задачи — иначе кеш не переиспользовался бы между задачами на
  одну и ту же зону), ключ кеша координаты+слой+версия данных+версия
  генератора в PostGIS. Параллельная генерация — `celery.group` на реальном
  воркере (`--concurrency=4`, отдельный процесс, настоящий Redis); повторный
  запрос того же батча подтверждённо берёт тайлы из кеша, не пересчитывая.
  Рельеф тайла — тот же метод квадратных призм (сетка 1 м) и то же
  многоструктурное сглаживание, что и Шаг 1.5, но по тайлам 250×250 м —
  единственный путь, где полный радиус 3 км при шаге 1 м реально тянется
  (~62,5 тыс. точек/тайл независимо от общего радиуса модели, в отличие от
  несвязанного `Delaunay` Шага 1.5). Стыковка рельефа между соседними
  тайлами — 0 м расхождения (шов сэмплируется без сглаживания, побитовое
  совпадение вершин + интерполяция по обе стороны, не только вершины).
  33 теста. Реального профиля на 3 км и многомашинного кластера не было —
  недоступно без пилота (0.1) и живой инфраструктуры.
- Шаг 2.2 (здания LOD2) — формы крыш (gabled/hipped/pyramidal/skillion) по
  `roof:*`, геометрия по ориентированному минимальному прямоугольнику
  контура — приём реальных рендереров OSM-3D (OSM2World/Simple3DBuildingsV1),
  проверено запросом к вики при разработке, не по памяти. Все объёмы солидов
  проверены точными замкнутыми формулами (не приближённо). Высота — водопад
  OSM→Overture→тип, источник явно в свойствах; доступа к датасету Overture
  в этой среде нет (`NullOvertureSource`, водопад настоящий, средний уровень
  не наполнен). Составные здания `building:part` — новая таблица импорта
  `osm_building_parts`, пространственное сопоставление с контуром
  (`shapely.intersects`, OSM явной ссылки не даёт); контур, покрытый хотя бы
  одной частью, не экструдируется сам (прямая цитата вики Key:building:part
  про поведение реальных 3D-рендереров), каждая часть — отдельный солид со
  своей высотой/крышей. Входы `entrance=*` — таблица `osm_entrances`, точки
  сопоставляются зданию/части буфером 1 м, записаны в `Pset_Здание` без новой
  геометрии. 62 теста на геометрию/крыши/составные здания/входы плюс два
  сквозных прогона реального конвейера до `site.ifc` (`roof:shape=gabled`,
  `building:part`+`entrance`). Критерий приёмки шага (90% зданий ближнего
  кольца с корректной формой крыши, выборка 30 реальных зданий) — нужен
  реальный пилот (0.1) для сверки с реальностью.
- Шаг 2.3 (дороги по полосам, п. 1-5) — подключён настоящий osm2streets
  (проект A/B Street): единственный существующий инструмент для геометрии
  полос/тротуаров/перекрёстков/разметки, переписывать заново не нужно и
  рискованно. Существует только как Rust/WASM (`osm2streets-js`) — вызывается
  отдельным процессом Node.js (`geo/osm2streets/`), как системный `osm2pgsql`
  в Шаге 1.1. Ключевая проблема: `osm2pgsql` не хранит связность узлов между
  дорогами — решена доп. колонкой `osm_roads.nodes` (ID узлов way) и
  восстановлением валидного OSM XML с настоящей топологией прямо из PostGIS,
  без повторного обращения к исходному `.osm`/`.pbf`. Результат — полосы,
  площадки перекрёстков и разметка (центральные линии, стрелки поворота из
  `turn:lanes`) в `site.ifc` (`Pset_Полоса`, `Pset_Перекрёсток`,
  `Pset_Разметка`), честным водопадом (нет `node`/пакета — участок остаётся с
  одной лентой на дорогу, Шаг 1.7, не падает). Разметки у одного перекрёстка
  сотни мелких штрихов — склеены в один меш/продукт на вид (`_combine_meshes`),
  иначе `site.ifc` распухнет; попутно найдена и исправлена настоящая проблема
  реальных данных osm2streets — самопересекающиеся полигоны разметки
  околонулевой площади валятся `shapely` без `make_valid` (та же природа, что
  у контуров зданий, Шаг 1.6). Бордюр 0,15 м (п. 2) — osm2streets его не
  выделяет отдельным типом полосы (проверено эмпирически), синтезирован по
  общей границе объединённых Driving- и Sidewalk-полос одной дороги (точная
  геометрия, не константное смещение), без бордюра на грунтовых дорогах
  (`surface` из вики Key:surface, раздел Unpaved — Шаг 2.3, п. 4). Покрытие
  (п. 4) — тег `surface=*` дороги переносится на каждую её полосу как есть
  (`Pset_Полоса.Покрытие`), тот же принцип, что `Pset_Дорога.Покрытие`
  (Шаг 1.7); при слиянии нескольких way в одну полосу (узел степени 2 — не
  настоящий перекрёсток, проверено эмпирически) берётся покрытие только
  первого найденного way. Посадка на рельеф с продольным сглаживанием и
  поперечным уклоном (п. 5) — своя ось у каждой полосы/штриха разметки
  (`relief.tin.long_axis_line`), сглаженный профиль вдоль неё (та же
  техника, что у дороги в TIN Шага 1.5 и у уровня вытянутого водоёма
  Шага 1.7) плюс типовой поперечный уклон 20 ‰; компактный фрагмент
  (площадка перекрёстка) — плоская посадка без профиля, направление для
  него физически не определено (`docs/pavement.md`). Разделитель и газон
  (остаток п. 2) — в отличие от бордюра, osm2streets отдаёт их САМ, без
  синтеза: `SharedLeftTurn` (полоса разворота, тег `lanes:both_ways=1` +
  `turn:lanes:both_ways=left`) и `Buffer(Verge)` (газон, тег
  `cycleway:<сторона>:separation:<сторона>=grass_verge`, проверено
  эмпирически) — оба проходят через общий код полос без отдельной ветки;
  единственная правка — газон физически трава, не покрытие проезжей части,
  поэтому `surface=*` дороги ему не наследуется (`_surface_for_lane`,
  `Покрытие=grass`). 24 теста на связность/геометрию/разметку/бордюр/
  покрытие/разделитель/газон плюс тесты на склейку мешей и на продольное
  сглаживание/поперечный уклон в `test_ifc_assemble.py` (31 тест всего в
  файле) плюс сквозной прогон реального перекрёстка через весь конвейер.
  Переходы из `crossing` не проверены (нужен более специфичный входной
  профиль); «колея» на грунтовых дорогах не реализована (геометрическая
  деталь профиля).
- Шаг 2.4 (каркасная и внутриквартальная сеть, п. 1, 4 и 5) — классификация
  (`geometry/road_network.py`): каркасная = `motorway…tertiary` с
  `_link`-съездами (по плану), иначе внутриквартальная. У дороги/полосы
  классификация по тегу `highway` (свой `osm_way_ids`); у перекрёстка/
  разметки своего way нет — геометрически, по факту касания уже
  классифицированной каркасной полосы. Два файла дорог (п. 4) —
  `build_site_ifc` получил `road_network_filter`: дороги/полосы/
  перекрёстки/разметка своей сети, без зданий/воды/ж-д/деревьев И без
  рельефа (TIN) — его меш при шаге сетки 1 м самый тяжёлый по памяти в
  сборке; первая версия прохода держала TIN в обоих файлах на каждую
  схему (меш пересобирался 6 раз за задачу вместо 2) — исправлено как
  реальная лишняя работа, хотя сам сквозной OOM в этой AI-сессии (см. ниже)
  это не сняло — он воспроизводится и на коде ДО этого шага. `assemble_ifc` кладёт
  `jobs/{id}/roads_{backbone,internal}_{ifc4,ifc4x3}.ifc` в Storage под
  ОТДЕЛЬНЫМ `model_id` в реестре GlobalId (иначе `ON CONFLICT` затёр бы
  GlobalId комбинированной модели). Каркасная — `Pset_Дорога/Полоса.
  Редактируемый=false`, внутриквартальная — `true`, буквально. Параметрическая
  внутриквартальная сеть (п. 5) — `RoadRibbon.axis` хранит исходную ось
  (только для одного цельного сегмента линии); `rebuild_road_ribbon`
  пересобирает ленту по новой оси с тем же профилем, отказывает на
  каркасной дороге и на дороге без сохранённой оси. Сверка с официальными
  перечнями дорог (п. 2) и импорт красных линий ИСОГД (п. 3) НЕ реализованы
  — оба требуют внешних данных, которых нет в этой среде (тот же честный
  статус, что у Шага 0.3). +12 тестов (`test_road_network_filter_*` реально
  валидируют каждый слой через `ifcopenshell.validate`); `test_api.py::
  test_full_happy_path_creates_downloadable_files` обновлён на новые файлы,
  но сам прогон в этой AI-сессии не подтверждён — упирается в потолок
  памяти контейнера (реальный `osm2pgsql` + рельеф 1 м + IFC + GLB в одном
  процессе), причём тот же OOM воспроизводится и на коде до Шага 2.4
  (`git stash` показал идентичное падение) — предсуществующее ограничение
  среды, не регрессия этого прохода.
- Шаг 2.5 (мосты, путепроводы, п. 1-3) — обнаружение по тегу `bridge=*`
  (`is_bridge`, исключаются из обычных лент); пролётное строение —
  ЛИНЕЙНАЯ интерполяция между отметками рельефа на двух концах оси (устои),
  не сглаженный профиль вдоль неё, как у дороги/воды — пролёт жёсткий, не
  следует рельефу под собой. Габарит проверяется в точке геометрического
  пересечения оси моста с осью другой (немостовой) дороги/пути (не выборкой
  по площади); свой норматив для дороги (5,0 м) и пути (6,0 м, строже —
  контактная сеть), типовые значения, не расчёт по нагрузке. При нарушении
  — пролёт поднимается на весь дефицит, `Pset_Мост.Статус=расчётный`, иначе
  `официальный`; без осей других объектов или без пересечения — проверка не
  выполняется, `Габарит_м` в файле отсутствует, не подставляется наугад.
  `IfcBridge` нативно в IFC4X3, прокси в IFC4; мост подчиняется
  `road_network_filter` (Шаг 2.4). Опоры по шагу, насыпи подходов (п. 4) и
