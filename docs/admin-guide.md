# Руководство администратора (Шаг 5.3, черновик)

**Статус: черновик AI** (план относит документацию к «BIM + AI
(черновики)», Шаг 5.3). Адресат — сотрудник OPS/администратор, который
разворачивает и эксплуатирует комплекс, не разработчик, читающий код.
Реальный прогон на сервере/в облаке этой инструкцией не подтверждён — в
среде разработки, где она написана, нет ни демона Docker, ни облачных
учётных данных, ни реального домена (см. `docs/ops.md`); все шаги ниже
описывают то, что реально проверено `docker compose config` и модульными/
интеграционными тестами, с честной пометкой там, где проверка остановилась
на этом уровне.

## 1. Развёртывание

Два файла compose, оверлей поверх базового:

```
docker compose -f infra/docker-compose.yml up -d          # разработка
docker compose -f infra/docker-compose.yml \
               -f infra/docker-compose.prod.yml up -d      # прод-надстройка
```

Базовый файл (`infra/docker-compose.yml`, Шаг 0.7) поднимает PostGIS,
Redis, MinIO и воркер. Надстройка (`infra/docker-compose.prod.yml`, Шаг
5.1) добавляет `api` (FastAPI-сервис), `caddy` (HTTPS), `postgres-exporter`/
`redis-exporter`/`node-exporter`/`prometheus`/`grafana` (мониторинг).

**Обязательные переменные окружения для прод-надстройки** (сборка
`docker compose config` честно падает без них — проверено реально, exit
code 1):

| Переменная | Назначение |
| --- | --- |
| `TOPOLOGY_DOMAIN` | Домен, на который Caddy выпустит сертификат Let's Encrypt. |
| `GRAFANA_ADMIN_PASSWORD` | Пароль администратора Grafana при первом запуске. |

Остальные (`POSTGRES_*`, `MINIO_*`) имеют рабочие значения по умолчанию из
`infra/.env.example`, для прода — заменить на реальные секреты.

**Разделение открытого и закрытого контуров** (п. 1 ТЗ 10.2): программная
часть — флаг `closed_contour_access` (Шаг 4.10) на уровне API, гейт
`require_closed_contour_access` перед выдачей данных сетей/изысканий.
Физическое разделение на уровне сети (отдельные серверы/VLAN для контуров)
— организационное решение при развёртывании, не настраивается в коде.

## 2. HTTPS

`infra/Caddyfile` — Caddy автоматически получает и продлевает сертификат
Let's Encrypt по протоколу ACME для домена из `TOPOLOGY_DOMAIN`. Ничего
вручную настраивать не нужно при наличии у сервера белого IP и открытых
портов 80/443 (ACME HTTP-01 challenge). Домен для Grafana —
`grafana.<TOPOLOGY_DOMAIN>` (отдельный поддомен, тот же сертификат-менеджер).

Реально проверено в этой среде: только генерация конфигурации
(`docker compose config`) — выпуск настоящего сертификата требует
публичного DNS-имени, которого здесь нет.

## 3. Мониторинг и оповещения

Prometheus (`infra/monitoring/prometheus.yml`) опрашивает раз в 30 с:

| Цель | Что измеряет | Замечание |
| --- | --- | --- |
| `topology-api:8000` | Метрики FastAPI-приложения | **Честно не готово**: точка `/metrics` в `api/app.py` не подключена (нужен ASGI-мидлварь, например `prometheus-fastapi-instrumentator`) — цель сконфигурирована заранее, данных пока не отдаёт. |
| `postgres-exporter:9187` | Состояние PostgreSQL (`pg_up` и др.) | Готово, стандартный экспортёр. |
| `redis-exporter:9121` | Состояние Redis | Готово, стандартный экспортёр. |
| `node-exporter:9100` | Диск/CPU/память хоста | Готово — нужен для правила `DiskSpaceLow` ниже. |

Правила оповещений (`infra/monitoring/alerts.yml`):

- **`ServiceDown`** (`up == 0`, `for: 2m`) — встроенная метрика Prometheus,
  доступна для любой цели `scrape_configs` без доработок приложения.
  Интервал опроса (30 с) + `for: 2m` математически гарантируют срабатывание
  не позднее ~2.5 мин с момента отказа — с запасом укладывается в критерий
  шага («≤ 5 мин»).
- **`PostgresDown`** (`pg_up == 0`, `for: 2m`) — то же самое, специфично
  для БД.
- **`DiskSpaceLow`** (свободно < 10 % от `node_filesystem_size_bytes`,
  `for: 5m`) — предупреждение о нехватке места (резервные копии и
  растровые данные не поместятся).

Grafana — визуализация поверх тех же метрик Prometheus. Готовые дашборды
для `postgres_exporter`/`redis_exporter`/`node_exporter` есть в публичной
галерее Grafana (grafana.com/grafana/dashboards) — подключаются по ID из
интерфейса Grafana при первом запуске, отдельных дашбордов в этот проход не
поставляется.

**Канал доставки оповещений** (Slack/email/Telegram) не выбран — зависит от
предпочтений эксплуатирующей команды; настраивается в Prometheus Alertmanager
(не включён в текущую надстройку) или напрямую в Grafana Alerting.

## 4. Резервное копирование и восстановление

```
# Резервная копия
POSTGRES_HOST=<хост> POSTGRES_USER=<юзер> POSTGRES_PASSWORD=<пароль> \
POSTGRES_DB=topology BACKUP_DIR=/var/backups/topology \
    infra/backup/backup_postgres.sh

# Восстановление (в НОВУЮ или существующую БД — существующая будет
# пересоздана)
POSTGRES_HOST=<хост> POSTGRES_USER=<юзер> POSTGRES_PASSWORD=<пароль> \
    infra/backup/restore_postgres.sh /var/backups/topology/topology_....dump [целевая_БД]
```

- `backup_postgres.sh` — `pg_dump --format=custom --compress=9`: сжатый
  дамп, поддерживает параллельное восстановление (в отличие от текстового
  SQL-дампа).
- `restore_postgres.sh` — пересоздаёт целевую БД (`DROP DATABASE ... WITH
  (FORCE)` + `CREATE DATABASE` + `CREATE EXTENSION postgis`), затем
  `pg_restore --jobs=$(nproc)` — параллельно, не однопоточно.
- Оба скрипта реально проверены (`geo/tests/test_ops_backup_restore.py`):
  настоящие данные → дамп → новая БД → восстановление → сверка полей
  совпадает. На тестовом объёме backup занял 0.20 с, restore — 1.29 с;
  на промышленном объёме реального пилота время будет больше — критерий
  шага («учебное восстановление ≤ 4 ч») стоит перепроверить реальным
  прогоном после появления пилотных данных (Шаг 0.1).
- **Расписание** — не встроено в скрипты (они самостоятельные, без
  демона): запускать `backup_postgres.sh` по cron/systemd timer с
  периодичностью по `docs/operations-policy.md` (раздел «Резервное
  копирование»).
- **MinIO** — `infra/backup/backup_minio.sh` написан (обёртка над `mc
  mirror`, стандартный приём самого MinIO), но НЕ проверен в этой среде
  (нет запущенного MinIO/клиента `mc`) — перед вводом в эксплуатацию нужен
  один пробный прогон на реальном MinIO.

## 5. Управление пользователями и ролями

- `PATCH /auth/users/{id}/role` (только администратор) — назначение роли
  («просмотр», «проектировщик», «администратор») и/или флага
  `closed_contour_access` (право на данные сетей/изысканий, отдельно от
  роли).
- Самостоятельная регистрация всегда даёт роль «просмотр» — повышение
  прав только вручную администратором, самоповышение запрещено (проверено
  тестом).
- Пароли — PBKDF2-HMAC-SHA256, 260 000 итераций (текущая рекомендация
  OWASP), не хранятся в открытом виде и не логируются.
- Отзыв доступа — `POST /auth/logout` отзывает токен сессии немедленно;
  для полного отзыва доступа пользователя — понизить роль/снять флаг
  закрытого контура через `PATCH /auth/users/{id}/role`.

## 6. Ключи доступа и вебхуки (внешние интеграции)

- Ключи (`X-API-Key`) — создаются через API, полное значение
  показывается ровно один раз при создании (принцип «показать один раз»,
  как у GitHub/Stripe); в базе хранится только SHA-256-хеш. При утере —
  создать новый ключ, старый можно отозвать.
- Вебхуки о готовности задачи — доставляются настоящим HTTP POST при
  переходе задачи в `done`/`failed`. Базовая защита от SSRF при
  регистрации URL (запрещены `localhost`/`0.0.0.0`/приватные адреса), но
  **не** защита от DNS rebinding или редиректов на приватные адреса — при
  регистрации вебхуков от третьих лиц эту доработку стоит учитывать.
  Доставка — без повторов при неудаче (нет очереди с ретраями).

## 7. Экспорт в Pilot-BIM

`PILOT_BIM_EXCHANGE_DIR` — переменная окружения, путь к папке обмена с
Pilot-BIM. Без неё эндпоинт `POST /jobs/{id}/export-to-pilot-bim` отдаёт
понятную ошибку `503`, а не падает непонятно. Прямая интеграция через API
Pilot-BIM не реализована (проприетарная платформа, нужна лицензия
заказчика).

## 8. Регламент обновления данных и обращений

См. `docs/operations-policy.md` — расписание обновления OSM/ограничений/
справочника РСО, порядок обработки обращений пользователей, план развития.

## 9. Честно: что нужно доделать перед реальной эксплуатацией

- Подключить `/metrics` в `api/app.py` (ASGI-мидлварь Prometheus) — без
  этого цель `topology-api` в мониторинге не отдаёт данных.
- Один реальный прогон `backup_minio.sh` на настоящем MinIO.
- Настроить канал доставки оповещений (Alertmanager/Grafana Alerting) —
  правила есть, доставки после срабатывания пока нет.
- Реальный сервер/облако, домен с публичным DNS — для настоящего
  Let's Encrypt-сертификата и реального прогона всей надстройки.
- Импортировать или собрать типовые дашборды Grafana для
  `postgres_exporter`/`redis_exporter`/`node_exporter`.
