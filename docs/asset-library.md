# Библиотека элементов (Шаг 2.8)

## Структура каталога (п. 1)

`geo/src/topology_geo/assets/manifest.json` — список записей, каждая
описывает категорию, тип, LOD, лицензию, источник и версию (дословно из
действия п. 1). Загрузка/поиск — `topology_geo.assets.library`
(`load_manifest`, `find_entry`, `entries_by_category`, `resolve_file`).

Две разновидности записи (`kind`):

- `"generator"` — параметрический генератор кода, `files` пуст, `source`
  указывает функцию-генератор в этом репозитории, `license` — «код проекта
  (см. LICENSE репозитория)».
- `"texture"` — готовый файловый актив (PBR-текстура, п. 4), `files`
  перечисляет реальные файлы под `geo/assets/`, `license="CC0"`.

Критерий проверки шага по плану — «у каждого элемента указана лицензия» —
проверяется тестом (`test_assets_library.py::
test_every_entry_has_non_empty_required_fields`, параметризован по всем
обязательным полям структуры, не только лицензии).

«Сцена использует элементы только ссылками» (второй критерий) —
`resolve_file(entry, filename)` возвращает ПУТЬ к файлу библиотеки
(`geo/assets/...`), не копирует и не встраивает содержимое; вызывающий код
(будущая сцена/сборка) читает файл по этому пути напрямую.

## Параметрические генераторы (п. 2)

Действие перечисляет: «опоры, столбы, бордюры, ограждения, пролёты,
фонари». К этому шагу три из шести типов уже были реализованы более
ранними шагами и просто занесены в каталог:

| Тип | Реализован в | Каталог |
| --- | --- | --- |
| Опора контактной сети | Шаг 2.6, `geometry.rail` | `pole_catenary` |
| Опора/башня ЛЭП | Шаг 2.7, `geometry.power` | `pole_power` |
| Бордюр | Шаг 2.3, п. 2, `geometry.streets` | `curb` |

Недостающие два типа реализованы этим шагом
(`geo/src/topology_geo/geometry/landscaping.py`, ранее не существовавший
модуль — `osm2pgsql` уже собирал `barrier=fence/wall` и `highway=
street_lamp` в таблицу `osm_landscaping` с Шага 1.1, но геометрического
генератора для них не было):

- **Ограждения** (`barrier=fence`) — упрощённо столбы через типовой пролёт
  (`FENCE_POST_SPACING_M=2,5 м`, действие буквально называет «пролёты»
  отдельным пунктом — здесь это параметр расстановки внутри генератора, не
  отдельная функция) плюс тонкий верхний поручень; распределены равномерно
  по всей длине линии, без обрубка последнего пролёта (тот же приём, что и
  у расчётной расстановки опор ЛЭП, Шаг 2.7). Собраны как `IfcRailing`
  (нативно в обеих схемах) — предопределённый тип `FENCE` есть только в
  `IfcRailingTypeEnum` IFC4X3 (проверено эмпирически через ifcopenshell);
  в IFC4 такого значения нет вовсе, поэтому там `USERDEFINED`, а не
  изобретённое несуществующее значение схемы.
- **Стены** (`barrier=wall`) — сплошная тонкая лента на всю высоту, `IfcWall`
  (нативно в обеих схемах, точное семантическое соответствие — не
  потребовался прокси, как у `IfcRoad`/`IfcBridge`).
- **Фонари** (`highway=street_lamp`) — столб + небольшая головка светильника,
  оба — тот же `mesh_cylinder`, что у деревьев и опор.

## Готовые модели с чистыми лицензиями (п. 3) — НЕ реализовано

Деревья основных пород средней полосы, МАФ (скамейки, урны, площадки),
остановки — как ГОТОВЫЕ (не параметрические) детальные 3D-модели с явно
проверенной лицензией. Это отдельная задача поиска, юридической проверки и
интеграции конкретных лицензированных мешей (в отличие от текстур,
у Poly Haven нет аналогично простого документированного API моделей,
покрывающего именно эти категории с гарантированно чистой лицензией) — не
выполнялась в этом проходе, честно не обещано. Деревья в конвейере
по-прежнему представлены упрощённым параметрическим стволом
(`geometry.vegetation`, Шаг 1.7), не готовой моделью.

## Текстуры PBR (п. 4) — реализовано, реальные файлы

5 материалов по действию плана — асфальт, плитка, грунт, газон, бетон.
Скачаны РЕАЛЬНО через документированный публичный API Poly Haven
(`api.polyhaven.com`/`dl.polyhaven.org`), лицензия CC0 (общественное
достояние, реальный источник, не выдуманные метаданные):

| Материал | Актив Poly Haven | Автор(ы) |
| --- | --- | --- |
| Асфальт | `asphalt_01` | Dario Barresi (обработка), Charlotte Baglioni (фотосъёмка) |
| Плитка | `checkered_pavement_tiles` | Amal Kumar |
| Грунт | `dirt` | Charlotte Baglioni |
| Газон | `grass_ground` | Charlotte Baglioni |
| Бетон | `brushed_concrete` | Dario Barresi (обработка), Dimitrios Savva (фотосъёмка) |

По три карты на материал, разрешение 1К (компромисс размера репозитория —
полный 8К комплект каждого материала весит сотни МБ):

- `diff_1k.jpg` — Diffuse/Albedo;
- `nor_gl_1k.jpg` — Normal (OpenGL-конвенция, совпадает с glTF/GLB —
  веб-вьюер, Шаг 1.9, конвертирует IFC в GLB);
- `arm_1k.jpg` — упакованная AO+Roughness+Metalness (glTF-конвенция ORM
  вместо трёх отдельных файлов).

Файлы лежат под `geo/assets/textures/<материал>/`, реально проверены тестом
(`test_texture_entries_reference_real_existing_files` — читает файл с диска
и проверяет ненулевой размер, не только запись в каталоге).

Применение текстур к конкретным поверхностям (например, покрытию проезжей
части в IFC/GLB-материалах) НЕ реализовано в этом проходе — текстуры
скачаны, легли в каталог с честной лицензией, но конвейер сборки IFC
(`ifc/assemble.py`) пока не назначает материалы поверхностям вообще (ни
цветом, ни текстурой) — это отдельная задача сборки/рендера.

## Представления IFC/рендер (п. 5)

У этого проекта пока нет отдельного пайплайна «детальная сетка для
рендера» (это ближе к Этапу 4 — Blender Cycles и т.п., Шаг 4.1+, не
достигнут). Представление в IFC (упрощённое тело) для параметрических
генераторов — единственное существующее представление; тот же меш после
конвертации в GLB (Шаг 1.9) используется и для веб-просмотра. Честно: п. 5
в буквальном прочтении («упрощённое тело» ОТДЕЛЬНО от «детальной сетки для
рендера») не реализован — секции не расходятся, второй сетки нет.

## Что НЕ входит в этот проход (сознательно, честно, не обещано)

- Готовые licensed 3D-модели (деревьев/МАФ/остановок) — п. 3.
- Назначение текстур конкретным поверхностям в сборке IFC/GLB.
- Отдельная детальная сетка для рендера, отличная от упрощённого IFC-тела.
- Версионирование каталога сверх текстового `version` поля (например, Git
  LFS/DVC для больших будущих активов) — при нынешнем объёме (13 МБ)
  обычный git достаточен.
