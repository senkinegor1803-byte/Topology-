# Выходные форматы (Шаг 2.10)

Три пункта плана: (1) федеративная структура IFC-файлов по слоям, (2)
дополнительные форматы (LandXML, DXF, CityJSON), (3) `meta.json` + упаковка
пакета выгрузки. Реализация — `geo/src/topology_geo/export/` (LandXML/
CityJSON/DXF), `ifc/assemble.py` + `jobs/steps.py::assemble_ifc` (федеративные
IFC-слои), `jobs/steps.py::package_outputs` (meta.json + zip).

## 1. Федеративные IFC-слои

На каждую IFC-схему (`IFC4`, `IFC4X3`) `assemble_ifc` теперь, кроме
комбинированного `site.ifc` и уже существующих (Шаг 2.4, п. 4)
`roads_backbone`/`roads_internal`, строит ещё три файла:

| Файл (Storage-ключ шага) | Содержимое | Своя TIN? |
| --- | --- | --- |
| `relief_{schema}.ifc` | Рельеф участка (TIN), тот же меш, что в `site.ifc` | да |
| `buildings_{schema}.ifc` | Только здания (LOD1/LOD2 по форме крыши) | нет |
| `power_{schema}.ifc` | ЛЭП: опоры, провода, подстанции, охранные зоны | нет |

Каждый — независимый `SiteModel` только со своим слоем (`ifc/assemble.py`,
`jobs/steps.py::assemble_ifc`), собранный уже готовыми объектами (без
пересчёта геометрии), под своим namespace реестра GlobalId — тот же приём,
что и `roads_backbone/internal` (Шаг 2.4, п. 4).

**Важная особенность памяти.** `roads_backbone`/`roads_internal` НАРОЧНО не
несут свой TIN (Шаг 2.4, п. 4) — включение рельефа в оба файла на каждую
схему было реальной причиной OOM при разработке того шага (сам меш на шаге
сетки 1 м — самая тяжёлая по памяти часть сборки). `relief_{schema}.ifc`
делает ровно то, от чего Шаг 2.4 уходил — пересобирает тот же меш ЕЩЁ раз на
каждую схему (итого TIN входит в IFC-продукты 4 раза за задачу вместо 2:
дважды в `site.ifc`, дважды в `relief_*.ifc`). Сделано осознанно (пункт плана
явно требует `relief.ifc` отдельным файлом), но это реальный дополнительный
расход памяти, а не только байт хранилища — честно фиксируем как известный
компромисс, не смягчаем формулировку.

`buildings_{schema}.ifc`/`power_{schema}.ifc` не несут TIN и от этого не
пострадали бы в норме (здания используют собственную `base_z`), НО опоры/
провода ЛЭП интерполируют высоту рельефа через `_terrain_elevation`
(`ifc/assemble.py`), которая при `site_model.tin is None` возвращает `0.0` —
то есть в файле `power_{schema}.ifc`, отдельно от комбинированного
`site.ifc`, опоры и провода стоят на условной плоскости z=0, НЕ на реальном
рельефе (в `site.ifc` рельеф есть, там высоты верны).

## 2. LandXML, CityJSON, DXF

Строятся ОДИН раз (не зависят от IFC-схемы) внутри `assemble_ifc`, из уже
готовых в памяти структур — та же экономия, что и у федеративных слоёв.

### LandXML (`export/landxml.py`)

Формат LandXML 1.2, написан вручную через `xml.etree.ElementTree` (открытая
XML-схема, специальная библиотека не нужна). Содержит:
- `<Surfaces><Surface>` — точки и треугольные грани уже готового TIN участка
  (Шаг 1.5), 1-based индексация точек (требование формата);
- `<Alignments><Alignment>` — по одному на дорогу/путь с непустой `axis`
  (Шаг 2.4/2.5: только объекты с ОДНИМ цельным сегментом линии); только
  прямые сегменты `<Line>` (без `Curve`/`Spiral` — входных данных о радиусе
  нет).

**Не входит:** координаты — локальные метры участка, БЕЗ формального
`<CoordinateSystem>`/EPSG (у МСК-59 в проекте нет декларированного
глобального кода, см. `coords.py`) — честнее не иметь поля, чем указать
неверный код. Открытие в реальной CAD/ГИС-программе (критерий проверки шага)
не проверено — нет доступа к такой программе в AI-сессии.

### CityJSON (`export/cityjson.py`)

CityJSON 1.1, обычный `dict` → `json.dumps`. Одно здание = один `Building`
CityObject с ТРЕМЯ геометриями (план явно требует «CityJSON (LOD0-2)»):
- LOD0 — плоский контур пятна застройки на отметке `base_z` (`MultiSurface`,
  БЕЗ экструзии — по определению LOD0: только «footprint», высота не
  участвует), кольцо с отверстиями дворов как есть, без триангуляции (плоский
  полигон, кольцо с отверстием допустимо напрямую в CityJSON);
- LOD1 — простая призма на всю высоту (`extrude_polygon_mesh`, форма крыши
  не учитывается — по определению LOD1);
- LOD2 — тот же меш, что и IFC-рендер зданий (`ifc/assemble.py`): плоская
  крыша → тот же `extrude_polygon_mesh`; скатная → `oriented_bounding_box` +
  `build_pitched_building_mesh`. Для плоской крыши LOD1 и LOD2 геометрически
  совпадают (не искусственно различены) — добавлены оба, чтобы у всех
  зданий был одинаковый набор LOD.

**Упрощения:** каждая треугольная грань меша — отдельная поверхность
`Solid`-границы (`[[i,j,k]]`), не объединённые плоские полигоны стен/ската
— валидно по спецификации, но многословнее. Список вершин ГЛОБАЛЬНЫЙ, без
дедупликации между зданиями. `transform` тождественный (`scale=[1,1,1]`,
`translate=[0,0,0]`), без целочисленного квантования координат.
`metadata.referenceSystem` (EPSG) не указывается — та же причина, что и у
LandXML.

### DXF (`export/dxf.py`)

Через `ezdxf` (новая зависимость пакета). Плоский 2D-чертёж в плане:
замкнутые `LWPOLYLINE` по трём слоям — «Здания» (контуры зданий, включая
отверстия дворов), «Дороги» (контуры дорожных лент), «Вода» (контуры
водоёмов и водотоков).

**Не входит (сознательно):** горизонтали рельефа (TIN есть, но контурные
линии по сечению плоскостями не строятся — отдельная задача); рельсовые
пути, ограждения, опоры ЛЭП, растительность (то же явно выбранное
подмножество, что и у LandXML/CityJSON, не «всё, что есть в IFC»); штриховка/
легенда/рамка листа/аннотации размеров — чертёж без оформления, только
геометрия по слоям.

## 3. `meta.json` и упаковка (`jobs/steps.py::package_outputs`)

Последний, лёгкий шаг конвейера (`DEFAULT_PIPELINE`) — скачивает уже
загруженные в Storage байты предыдущих шагов и упаковывает их в
`jobs/{id}/package.zip`, БЕЗ пересборки TIN/геометрии.

`meta.json` (схема `schemas/meta.schema.json`, Шаг 0.8) заполняется из:
- `task_id`/`center`/`radius_m` — поля задачи;
- `generator_version` — `topology_geo.__version__`;
- `coordinate_system.base_point` — сохранён в результате `assemble_ifc` (не
  пересчитывается через TIN заново — интерполяция требовала бы перестройки
  TIN, самой тяжёлой части сборки);
- `layers` — список слоёв пакета, статус `"расчётно"` у ВСЕХ (ни один слой
  не является официальными регуляторными данными — те появятся в Этапе 3,
  завышать статус нечестно); `"networks"`/`"constraints"` не перечислены —
  их ещё нет (Шаги 3.1/3.4);
- `files` — все файлы архива с реальным `size_bytes` (посчитан при упаковке);
- `sources` — РЕАЛЬНЫЙ журнал: `osm_import_log` (Шаг 1.1, п. 4, лицензия
  OSM — известная константа ODbL) и `dem_coverage` (Шаг 1.2, п. 4, для bbox
  задачи). У рельефа лицензия НЕ хранится в реестре покрытия (поле
  отсутствует в схеме таблицы) — честно помечена как не зафиксированная, не
  придумана.

**Переименование `roads_internal` → `roads_local`.** Внутри `assemble_ifc`
файл называется `roads_internal_{schema}.ifc` (историческое имя Шага 2.4).
`docs/data-dictionary.md` §4 называет итоговый файл пакета `roads_local.ifc`
и явно предусматривает, что Шаг 2.10 сведёт имена — переименование сделано
именно на границе упаковки (`package_outputs` кладёт в архив
`roads_local_{schema}.ifc`), внутренний Storage-ключ шага не переименован
(риск затронуть уже стабильный код/тесты Шага 2.4 ради чистого
наименования не оправдан).

**Формат `XKT`** упомянут в `schemas/meta.schema.json` (`files[].format`
enum), но НЕ производится этим шагом — конвертер `IFC → XKT` не
реализовывался (за рамками Шага 2.10, отдельный инструмент `xeokit`).

## Что не входит в этот проход (честно)

- Отдельный `vegetation.ifc` федеративный файл — растительность есть только
  внутри комбинированного `site.ifc`, своего федеративного файла в этом
  проходе не получила (список примеров плана называет `relief.ifc`/
  `buildings.ifc`/`power.ifc`, `vegetation.ifc` — нет).
- `networks.ifc`/`constraints.ifc` — заблокированы на Шагах 3.1/3.4 (Этап 3
  ещё не начат).
- Реальное открытие LandXML/DXF/CityJSON в целевой CAD/ГИС-программе
  (критерий проверки шага) — недоступно AI-сессии без человека и такой
  программы.
- Горизонтали рельефа в DXF, целочисленное квантование координат CityJSON,
  геопривязка (EPSG) LandXML/CityJSON — см. разделы выше.
