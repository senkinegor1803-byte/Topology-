# Потоковый веб-просмотр (Шаг 2.11)

Три пункта плана: (1) генерация 3D Tiles с иерархией детализации, (2)
загрузка во вьюер по мере приближения, (3) сохранение панели свойств и
слоёв из Этапа 1. Реализация — `geo/src/topology_geo/tiling/{gltf_mesh,
tile_content,tileset}.py` (генерация), `jobs/steps.py::generate_tileset`
(шаг конвейера), `web/viewer/index.html` (вьюер, режим `?tileset=`).

## 1. Генерация 3D Tiles

Переиспользует инфраструктуру Шага 2.1 (`tiling.grid`/`tiling.terrain`), а
не строит собственную: тайлы 250×250 м (`tiling.grid.tiles_covering_
circle`), рельеф тайла — `tiling.terrain.build_tile_terrain` (та же
функция, что и параллельный генератор тайлов Шага 2.1, `tasks.tile_
tasks`). Здания — та же меш-логика по LOD, что и CityJSON (Шаг 2.10,
`export.cityjson`): без крыши/блоком/с крышей.

**Иерархия детализации** — по кольцам LOD (Шаг 2.1, п. 1: `classify_lod_
ring`, границы 500/1500/3000 м), НЕ по вложенной REPLACE-иерархии 3D
Tiles: плоский список тайлов-листьев под общим корнем-группой (`refine:
"ADD"`). Вложенный REPLACE не подошёл бы честно — концентрические кольца
не образуют классическое дерево «ребёнок полностью покрывает площадь
родителя» (внутреннее кольцо меньше внешнего), а искусственно подгонять
геометрию под это дерево — заведомо усложнение ради формы, не сути.

Реальное снижение детализации с расстоянием — не просто разметка одним
именем: шаг фоновой сетки рельефа растёт по кольцу (`tiling.tileset.
RING_BACKGROUND_STEP_M`: LOD2 — 1 м, как и раньше; LOD1 — 5 м; LOD0 —
15 м), здания на дальнем кольце — плоский контур без экструзии (LOD0), на
среднем — блок на всю высоту без крыши (LOD1), на ближнем — с формой
крыши (LOD2, та же геометрия, что в IFC/CityJSON). `geometricError` тайла
= этот шаг сетки — честная метрика (крупнее шаг → грубее приближение →
больше мировая ошибка), не произвольное число.

**Лёгкий шаг конвейера.** `generate_tileset` НЕ строит общий TIN участка
(самая тяжёлая по памяти часть `assemble_ifc`, см. `docs/output-
formats.md`) — рельеф тайла берётся напрямую из уже сохранённого растра
(`prepare_relief`), здания экструдируются из уже посчитанной выборки без
общего TIN (высота площадки — билинейно прямо из растра, `relief.tin.
sample_bilinear`, не через `SiteTin.interpolate_z`).

**Честно не входит в этот проход:** дороги/вода/рельсы/растительность/ЛЭП
в тайлах (только рельеф и здания — те слои, у которых уже есть готовая
многоуровневая меш-логика для переиспользования); кэш тайлов (Шаг 2.1,
`tiling.cache`) этим шагом не используется — каждый вызов `generate_
tileset` строит все тайлы заново, не переиспользуя уже посчитанные
(подключить кэш можно отдельно, не меняя формат `tileset.json`).

## 2. Загрузка по мере приближения

Свой вьюер проекта (three.js, не Cesium) не реализует полный расчёт
screen-space error по спецификации 3D Tiles — вместо этого простое,
честно документированное правило (`web/viewer/index.html`,
`loadTileset`): чем БЛИЖЕ камера к ЦЕНТРУ УЧАСТКА (не к каждому тайлу по
отдельности), тем более детальные кольца догружаются — `RING_LOAD_
DISTANCE_M = {LOD0: 3400, LOD1: 1800, LOD2: 800}` (метры от камеры до
центра участка). Проверка — раз в 500 мс (`setInterval`), не на каждый
кадр (`fetch` не бесплатный). Выгрузка тайлов при отдалении камеры НЕ
реализована (простая первая версия — тайлы, однажды загруженные, остаются
в сцене; при всего 3 кольцах на задачу это не проблема памяти на клиенте).

URL отдельного тайла собирается из URL самого `tileset.json` (тот же
`/models/{job}/download?key=...`, Шаг 1.3): базовый путь без query +
`?key=<ключ тайла из content.uri>` — так вьюеру не нужно знать структуру
Storage-ключей заранее, только сам `job`.

## 3. Панель свойств и слоёв (сохранена из Этапа 1)

Дерево объектов/слоёв (Шаг 1.9, п. 2) строится ТЕМ ЖЕ кодом (`buildTree`),
что и в режиме `?model=` — тайлы, загружаясь по одному, переносят свои
узлы-категории («Рельеф»/«Здания» каждого тайла) в ОБЩИЕ узлы-папки на всю
модель (`categoryGroup`, реальные `THREE.Group` в сцене, не плоский
список — иначе переключатель видимости слоя ничего бы не выключал).
Панель свойств по клику — тот же `renderProperties`, без изменений;
содержимое тайла не несёт IFC `GlobalId`/`Pset` (это не IFC-модель, сырая
геометрия) — для него честно показывается «У объекта нет IFC-свойств»,
как и для любого объекта без `userData.globalId` в существующем коде.

## Проверка (`docs/plan.md`)

- «Первый кадр ≤ 5 с»: проверено — headless Chromium/Playwright реально
  загружает `tileset.json` + тайлы и показывает первую партию за ≤ 5 с
  (`test_viewer_tileset_browser.py::test_tileset_viewer_loads_within_
  five_seconds`). Это НЕ то же самое, что «первый кадр рендера на реальном
  устройстве» — измеряется момент готовности первой партии контента, не
  фактический кадр GPU.
- «≥ 30 кадров/с на ноутбуке со встроенной графикой»: НЕ проверено и не
  может быть проверено в AI-сессии — нет реального устройства/GPU,
  headless-браузер в контейнере рендерит программным растеризатором с
  непредсказуемой к реальному железу частотой кадров. Честно не заявляется.

## Что не входит в этот проход (честно)

- Дороги/вода/рельсы/растительность/ЛЭП в тайлах (только рельеф+здания).
- Кэш тайлов Шага 2.1 не подключён к `generate_tileset` (каждый вызов
  строит тайлы заново).
- Полный расчёт screen-space error по спецификации 3D Tiles (простое
  правило по расстоянию до центра участка вместо него).
- Выгрузка тайлов при отдалении камеры (память клиента).
- Реальная проверка частоты кадров на целевом оборудовании.
