# Личный кабинет (Шаг 4.10)

`geo/src/topology_geo/auth/store.py` (данные) + добавления в
`geo/src/topology_geo/api/app.py` (эндпоинты).

## Авторизация и роли (п. 1)

Настоящий пароль-хеш через `hashlib.pbkdf2_hmac("sha256", ..., 260_000
итераций)` (текущая рекомендация OWASP), соль — `secrets.token_bytes(16)`,
сравнение — `secrets.compare_digest` (защита от timing-атак). Токены сессий
— `secrets.token_urlsafe(32)`, срок жизни 24 ч, хранятся в отдельной таблице
`sessions` (не JWT — нет отдельного сервиса для валидации подписи, простая
таблица с `expires_at` для однопроцессного FastAPI+Postgres проще и так же
надёжна для отзыва по требованию, `POST /auth/logout`).

**Роли** (буквально по плану): `"просмотр"`, `"проектировщик"`,
`"администратор"`. **«Доступ к закрытому контуру»** — НЕ четвёртая роль, а
булев флаг поверх ролей: по формулировке самого плана (п. 10.4 ТЗ — «доступ
к сетям и изысканиям — только по ролям») это ПРАВО на определённые данные,
а не должность вроде «проектировщик». Самостоятельная регистрация всегда
даёт роль «просмотр»; повышение — только через `PATCH
/auth/users/{id}/role`, доступный лишь администратору (`require_admin`).

Демонстрация того, что флаг `closed_contour_access` реально что-то
закрывает, а не просто хранится: `GET /projects/{job_id}/closed-contour`
(гейт `require_closed_contour_access`) выполняет настоящий запрос
официальных ограничений (Шаг 3.1, `constraints.store.find_zones`) по
реальному bbox задачи (точный geodesic-пересчёт через МСК-59,
`coords.wgs84_to_msk59`/`msk59_to_wgs84`, не приближение градус↔метр) — без
права 403, с правом — реальные зоны.

## Проекты (п. 2)

`GET /projects` — задачи текущего пользователя. Владение — ОТДЕЛЬНАЯ
таблица `job_ownership` (не колонка `jobs.owner_id`): `jobs/store.py` уже
используется десятками тестов Шагов 1.3-3.13, добавление обязательной
колонки с внешним ключом на новую таблицу `users` создало бы обратную
миграционную зависимость (003 → 010) и требовало бы менять `create_job` —
риск регрессии по всему проекту. Таблица-связка — тот же приём расширения
без изменения существующей схемы, что уже применялся в проекте.

`POST /jobs` принимает `Authorization: Bearer <token>` НЕОБЯЗАТЕЛЬНО: без
заголовка — анонимная задача (существующее поведение Шага 1.3, ни один
старый тест не передаёт заголовок, реально перепроверено — регрессий нет);
с валидным токеном — задача сразу привязывается к пользователю.

**Честно не реализовано:** «версии, ЖК, запросы ТУ, рендеры» одной
задачи (действие плана) НЕ сведены в ответ `/projects` — данные Шагов
3.6-3.12 (посадка ЖК, реестр ТУ) и Шага 4.5 (рендеры) не хранят ссылку на
`jobs.id` в своих текущих схемах; свести их воедино — отдельная
интеграционная работа (добавить `job_id` в каждую из этих схем), не часть
этого прохода.

## Статусы и уведомления (п. 3)

Реальный хук в `tasks/pipeline_tasks.py::run_job_step_task`: в момент,
когда статус задачи становится терминальным (`done`/`failed`), если у
задачи есть владелец (`job_ownership`), создаётся строка в `notifications`
— проверено сквозным тестом (`test_job_completion_creates_notification_for_
owner`): задача без seed-данных OSM реально падает (тот же сценарий, что
`test_create_job_then_get_shows_failed_without_seed_data` в `test_api.py`),
уведомление реально появляется в `GET /me/notifications`.

**Честно:** «с прогрессом» — только терминальные статусы (done/failed)
порождают уведомление, промежуточный прогресс по шагам не уведомляет
(частые уведомления на каждый шаг были бы шумом без реального push-канала
— WebSocket/SSE не реализованы, клиент опрашивает `GET /jobs/{id}` сам,
как и до этого шага).

## Скачивание и публичные ссылки (п. 4)

Скачивание файлов комплекта — уже существующий `GET
/models/{job_id}/download` (Шаг 1.3), не изменён. Публичные ссылки — новая
таблица `public_links` (`token` → `job_id`, отзываемый), `POST
/jobs/{job_id}/share` (только владелец задачи), `GET /public/{token}` —
находит первый файл с `viewer_url` (`GET /models/{id}/files`) и
перенаправляет во вьюер.

**Честно: это не новая граница безопасности.** Остальные эндпоинты задачи
(`GET /jobs/{id}`, скачивание файлов) и без того не требуют авторизации —
в проекте пока нет ролевого разграничения доступа к уже существующим
эндпоинтам (это отдельная, более инвазивная работа: потребовала бы
добавить обязательную проверку владельца/публичности к `GET /jobs/{id}` и
`GET /models/{id}/download`, что меняет поведение для всех существующих
клиентов и рискует множеством регрессий по уже широко протестированному
API Шага 1.3). Публичная ссылка здесь — стабильный, отзываемый,
предсказуемый URL для удобства (вьюер, а не голый `job_id` в адресной
строке), а не механизм скрытия/открытия данных, которые и так не скрыты.

## Тесты

21 тест на реальном FastAPI `TestClient` + Postgres
(`test_api_auth.py`) — регистрация/логин/логаут, роли и их проверка
(в т.ч. запрет самоповышения), анонимное создание задачи (регрессия),
создание задачи с токеном → появление в `/projects`, изоляция проектов
между пользователями, реальное уведомление о падении задачи, публичные
ссылки (создание/чужой job/404 без готовой модели/неизвестный токен),
закрытый контур (403 без права, реальные зоны с правом). Плюс 15
модуль-тестов хранилища (`test_auth_store.py`, включая хеширование
пароля, сессии, владение, уведомления, публичные ссылки) и SQL-синхронизация
(`test_auth_sql_migrations.py`). Существующие тесты `test_api.py`
перепроверены без регрессий после добавления авторизации и хука
уведомлений в `pipeline_tasks.py`.

## Что не проверено

Критерий шага («новый пользователь проходит путь ... без инструкции за
30 мин») требует реального фронтенда личного кабинета (SPA/страницы) и
живого пользователя — этот проход строит только backend API; отдельная
страница личного кабинета (аналог `web/viewer`/`web/panorama`) не
построена в этом проходе.
