## 1. Системы координат и высот (Шаг 0.4) — реализовано

Код: `geo/src/topology_geo/coords.py`. Тесты: `geo/tests/test_coords.py`.

### 1.1 Плоские координаты: WGS-84 → МСК-59

Композиция двух классических геодезических преобразований:

**(a) 7-параметрический сдвиг Гельмгольца (Helmert, position-vector)** между
эллипсоидами Красовского и WGS-84 в геоцентрических координатах:

```
[X']   [1   -rz   ry ]   [X]   [dx]
[Y'] = [rz   1   -rx ] · [Y] + [dy]   · (1 + ds·1e-6)
[Z']   [-ry  rx   1  ]   [Z]   [dz]
```

где `(dx,dy,dz) = (23.57, -140.95, -79.8)` м, `(rx,ry,rz) = (0, 0.35, 0.79)`
угловых секунд, `ds = -0.22` ppm — параметры СК-63 → WGS-84, общие для всех
зон МСК-59 (см. `docs/coordinate-systems.md` про источник и статус
подтверждения).

**(b) Проекция Гаусса-Крюгера (Transverse Mercator)** эллипсоида Красовского
на плоскость зоны:

```
x = X0 + k0 · [проекция TM с осевым меридианом lon0]
y = Y0 + k0 · [...]
```

с параметрами по зоне `z ∈ {1,2,3}`:

| z | lon0 | X0 | Y0 | k0 |
| - | ---- | -- | -- | -- |
| 1 | 53.55° | 1 250 000 | −5 914 743.504 | 1 |
| 2 | 56.55° | 2 250 000 | −5 914 743.504 | 1 |
| 3 | 59.55° | 3 250 000 | −5 914 743.504 | 1 |

Реализация не переписывает формулы TM/Гельмерта вручную — они делегированы
библиотеке PROJ через `pyproj.CRS.from_proj4(...)` (`coords.MskZoneParams.to_proj4`),
это единственный источник истины по самой проекции; код проекта отвечает
только за выбор зоны и параметров.

**Выбор зоны:** `zone(lon) = argmin_z |lon - lon0(z)|`, с отбраковкой при
`|lon - lon0(z)| > 2°` (участок вне Пермского края) — `pick_msk59_zone`.

### 1.2 Высоты: EGM96 → Балтийская система

Локальная модель — аффинная (наклонная плоскость) поправка в проекционных
координатах зоны, откалиброванная по контрольным точкам:

```
h_target(lon, lat) = h_source + c0 + c1·(x - x0) + c2·(y - y0)
```

где `(x0, y0)` — проекция первой контрольной точки, `(c0, c1, c2)` находятся
методом наименьших квадратов по всем точкам с известными `h_source, h_target`
(`fit_height_offset`, решение системы нормальных уравнений 3×3
`_solve_3x3`). При <3 точках модель вырождается в константу `c0 = mean(Δh)`,
`c1 = c2 = 0`.

Критерии приёмки Шага 0.4 — функции проверки:

- `verify_planimetric`: `error_m = sqrt(dx² + dy²) ≤ 0.1 м` на точку;
- `verify_heights`: `error_m = |h_predicted - h_target| ≤ 0.05 м` на точку.

Обе проверки в тестах прогнаны на синтетических точках (самосогласованность
кода); реальная калибровка ждёт данные изысканий (см. `docs/coordinate-systems.md`).

## 2. Геометрия участка и конвейера (Этап 1) — заготовка

Формулы ниже фиксируют то, что уже задано критериями плана (радиусы, допуски,
размеры), чтобы реализация в `geo/` следовала одной согласованной модели, а не
придумывалась заново на каждом шаге. Реализуется в Шагах 1.4–1.8.

### 2.1 Буфер выборки

Для центра участка `c = (x_c, y_c)` в МСК-59 и радиуса задачи `R ∈ [500, 3000]` м
(Шаг 1.4, п. 1):

```
buffer_radius = R + margin,   margin = 50 м
select = { объект | dist(объект, c) ≤ buffer_radius }
```

Обрезка по кругу — на радиусе `R` (без запаса), запас 50 м только для выборки
из PostGIS, чтобы не терять объекты, чьи части попадают в круг.

**Реализовано (Шаг 1.4):** `selection.query.fetch_features_in_buffer` — сам
буфер (формула выше, через `geography`-фильтр в PostGIS, WGS-84);
`selection.clip.clip_and_localize` — обрезка кругом ровно радиуса `R` и
перевод в локальные координаты:

```
local(p) = (x(p) - x_c, y(p) - y_c),   p после обрезки geom ∩ circle(c, R)
```

в проекционных координатах (МСК-59), после `coords.transform_geometry_to_msk59`.

**Реализовано раньше срока (Шаг 1.3):** перевод радиуса `R` (метры) в bbox
WGS-84 для `relief.service.get_dem` — не наивный градусный отступ (искажается
с широтой), а через проекцию в МСК-59 и обратно:
`corner_wgs84 = msk59_to_wgs84(x_c ± R', y_c ± R', zone)`, где
`R' = R + margin` — см. `jobs.steps._wgs84_bbox_for_radius`.

### 2.3 Тайлы (Шаг 2.1) — реализовано

Код: `geo/src/topology_geo/tiling/{grid,cache,terrain}.py`,
`geo/src/topology_geo/tasks/tile_tasks.py`. Тесты: `geo/tests/test_tiling_*.py`,
`geo/tests/test_tile_tasks.py`.

Территория разбивается на квадраты `250×250` м в МИРОВЫХ координатах МСК-59
зоны (не в локальных координатах задачи, которые у каждой задачи свои, а не
в условной базовой точке проекта — иначе один и тот же физический тайл,
запрошенный из двух разных задач, не совпал бы по ключу и кеш никогда бы не
сработал; сетка выровнена от истинного нуля проекции зоны, `(x0, y0) = (0, 0)`):

```
tile_x = floor(x_world / 250)
tile_y = floor(y_world / 250)
tile_key = f"msk59-{zone}/250/{tile_x}_{tile_y}/{layer}/{data_version}/{generator_version}"
```

`layer` — часть ключа, не только описательная колонка: рельеф (Шаг 2.1),
здания LOD2 (Шаг 2.2), дороги по полосам (Шаг 2.3) одного и того же квадрата
— независимые артефакты со своим циклом обновления (регенерация дорог не
должна протухать кеш рельефа того же тайла).

**Стыковка тайлов без щели (п. 4 шага)** — тот же приём «врезки», что и в
§2.4 (TIN участка Этапа 1): граничные точки тайла сэмплируются на сетке,
привязанной к ФИКСИРОВАННОМУ шагу от границы квадрата (`boundary_step_m`,
по умолчанию 1 м, как и фоновая сетка — §2.4), а не к произвольному шагу
фоновой сетки. Шов сэмплируется БЕЗ сглаживания (в отличие от фона того же
тайла, §2.4) — иначе краевой эффект сглаживания у границы тайла дал бы
разным соседям разные значения в одной мировой точке, и щель вернулась бы
уже от сглаживания, а не от шага сетки. Два соседних
тайла делят общее ребро (одинаковые мировые координаты по построению) и
сэмплируют один и тот же растр рельефа в одних и тех же точках — значит
получают побитово одинаковые `(x, y, z)` вдоль шва. Проверено не на глаз:
`test_adjacent_tiles_share_identical_terrain_along_horizontal_seam`/
`..._vertical_seam` сравнивают множества вершин шва на равенство (не
приближённое), плюс `test_tile_terrain_interpolation_has_no_gap_across_seam`
проверяет интерполяцию высоты по обе стороны шва, а не только вершины.

**Параллельная генерация и кеш (п. 3 шага)** — `tasks/tile_tasks.py`:
`generate_terrain_tile_task` сперва проверяет кеш (`tiling.cache.find_cached_tile`)
и возвращает готовый тайл без пересчёта; `generate_terrain_tiles_parallel`
ставит весь батч в очередь разом через `celery.group` — Celery распределяет
задачи по всем подключённым воркерам. Проверено на реальном воркере
(`--concurrency=4`, отдельный процесс, настоящий Redis-брокер): батч из 4
тайлов собирается параллельно, повторный запрос того же батча не меняет
`created_at` в PostGIS (кеш, а не пересчёт).

Кэш переиспользуется, если ключ (включая версии данных и генератора) совпал.

### 2.4 Рельеф: адаптивный TIN и сшивка (Шаги 1.2, 1.5) — реализовано

Код: `geo/src/topology_geo/relief/tin.py`. Тесты: `geo/tests/test_relief_tin.py`.

- Плотность точек — не непрерывная функция расстояния, а конструктивный
  приём: вдоль дорог/воды/зданий явно добавляются точки ровно на объекте
  (шаг `road_step_m`, по умолчанию 1 м), а фоновая сетка (`background_step_m`,
  по умолчанию 1 м — «метод квадратных призм» инженерной геодезии: ячейка
  сетки — квадрат в плане, два треугольника Делоне на ячейку) их зоны не
  покрывает — то есть плотность выше именно там, где есть характерные линии,
  без отдельной функции `f(dist)`.
- Многоструктурное сглаживание фона (после шага 1 м, чтобы убрать шум/
  ступеньки источника без потери самой сетки): 2D-скользящее среднее по
  окну `w_bg` (по умолчанию 5 м) отдельно для фона, отдельно от 1D-сглаживания
  дороги вдоль оси и отдельно от воды/зданий (те не сглаживаются вовсе —
  их отметка обязана остаться точной, см. ниже):

```
z_smooth(i,j) = (1/N) · Σ z_raw(i+di, j+dj)   по (di,dj) в окне ⌈w_bg/step⌉×⌈w_bg/step⌉, N — число заполненных ячеек окна
```

  Для линейного рельефа (плоскость) среднее по симметричному окну равно
  значению в центре — сглаживание не смещает наклон, только гасит
  высокочастотный шум (`geo/tests/test_relief_tin.py::test_smooth_grid_elevations_preserves_plane_away_from_edges`).
  Окно строится на сетке, расширенной на `⌊w_bg/step/2⌋` шагов за пределы
  участка/тайла и обрезанной обратно — иначе `mode="nearest"` у самого края
  повторял бы крайний семпл вместо реального соседнего пикселя, что на
  наклонной плоскости даёт систематическое смещение (тот же эффект, что и
  несимметричное окно у сглаживания дороги, решён иначе — реальным запасом
  растра, а не линейной экстраполяцией).
- Ограничение масштаба: несвязанный (нетайловый) `Delaunay` на всех точках
  участка сразу не тянет большой радиус при шаге 1 м — реальный прогон
  показал ~14 с/1.5 ГБ на 500 м (испытанный радиус MVP, Этап 1), но уже
  >12 ГБ и рост на 1.5 км (~7 млн точек). `build_site_tin` поэтому отказывает
  явной ошибкой выше `MAX_BACKGROUND_POINTS_UNTILED` (~800 м при шаге 1 м) —
  для большего радиуса нужен тайловый путь §2.3/Шага 2.1
  (`tiling/terrain.py`), где тот же принцип применяется по тайлам 250×250 м
  независимо от общего радиуса модели.
- «Врезка» дорог/воды/зданий — точки-разрывы (breakline) с заранее посчитанной
  «правильной» отметкой попадают в ОБЩИЙ набор точек триангуляции Делоне,
  поэтому дорога/вода/площадка становятся частью самой сетки:
  - дорога: отметка = скользящее среднее рельефа вдоль оси (шаг п.2 плана,
    «продольный — сглаживание»), с линейной экстраполяцией на краях линии
    (без нее несимметричное окно смещает отметку пропорционально уклону —
    реальная находка при разработке, см. регрессионный тест
    `test_road_stays_within_tolerance_after_edge_padding`);
  - вода/здание: отметка = `min` рельефа по границе полигона (урез/площадка),
    единая по всему контуру.
- Барицентрическая интерполяция по треугольнику Делоне (`SiteTin.interpolate_z`)
  — на плоском тестовом рельефе воспроизводит его точно (см. тест
  `test_tin_reproduces_plane_on_background_terrain`), что и подтверждает
  корректность выборки координат: до найденного при разработке бага (смещение
  на полпикселя при чтении растра, `sample_bilinear` путал угол пикселя с его
  центром) интерполяция систематически ошибалась на доли метра — сейчас
  исправлено и покрыто регрессией.
- Контроль треугольников (Шаг 1.5, п. 3): самопересечений триангуляция Делоне
  не даёт по построению; вырожденные (нулевой площади) грани отлавливает
  `find_degenerate_triangles` после дедупликации близких точек.
- Критерий приёмки («дорога не висит и не уходит глубже 0.1 м») —
  `max_deviation_along_line`; на синтетическом плоском рельефе отклонение
  практически нулевое (см. тест), на реальном рельефе проверяется тем же
  инструментом после выбора пилота (Шаг 0.1).
- Сшивка разнородных источников рельефа (топосъёмка приоритетнее TessaDEM,
  Шаг 1.2 п. 3): в полосе шириной `w ∈ [30, 50]` м вокруг границы источника
  высота — линейная интерполяция веса:

```
h(p) = α(p)·h_survey(p) + (1-α(p))·h_dem(p),   α(p) = clamp(dist_to_boundary(p) / w, 0, 1)
```

внутрь области съёмки `α → 1`, наружу `α → 0`; критерий приёмки — отсутствие
«ступеньки» (разрыва первой производной) > 0.2 м.

### 2.5 Здания: высота и низ (Шаг 1.6, водопад расширен Шагом 2.2) — реализовано

Код: `geo/src/topology_geo/geometry/buildings.py`. Тесты:
`geo/tests/test_geometry_buildings.py` (35 тестов, включая составные здания и
входы — §2.11).

```
height(building) = tag(height)                                  [источник = "OSM"]
                  or tag(building:levels) · 3 + 1                [источник = "OSM"]
                  or overture_source.lookup(osm_id, footprint)   [источник = "Overture", Шаг 2.2 п.2]
                  or default_height(building_type)               [источник = "тип (умолчание)"]

z_base(building) = min(relief(p) for p in footprint)
```

`default_height(type)` — таблица по частым значениям `building=*`
(`DEFAULT_HEIGHT_BY_TYPE`), с общим резервом 9 м для остальных типов; и то,
и другое — рабочее приближение, подлежит уточнению по факту (план явно
требует «выборочную сверку 20 высот с реальностью» — задача для реального
пилота, Шаг 0.1). Исправление геометрии контура (п. 3 Шага 1.6) —
`repair_footprint`: `shapely.make_valid` на самопересечениях, дедупликация
соседних точек, приведение внешнего кольца к единой ориентации (против
часовой стрелки).

Источник отмечается явно в свойствах (`Pset_Здание.Источник_высоты`, Шаг 2.2,
п. 2), не только флагом факт/умолчание — план требует различать OSM и
Overture, оба «факт», но разные по происхождению. `OvertureHeightSource` —
протокол; `NullOvertureSource` (реально подключённая реализация в
`jobs.steps.assemble_ifc`) всегда возвращает `None` — доступа к датасету
Overture Buildings в этой среде нет (не настроено сетевое/BigQuery-
подключение к его хранилищу), водопад падает на дефолт по типу; подключение
реального источника не потребует изменений в `compute_height_m`.

### 2.6 Огибающая допустимой застройки (Шаг 3.3) — заготовка

Булева/геометрическая модель, формализуется при реализации Этапа 3:

```
envelope = (parcel ⊖ setbacks) \ (⋃ protection_zones ∪ ⋃ forbidden_zones)
height_limit = min(height_limit_pzz, height_limit_airport, height_limit_okn)
```

где `⊖` — эрозия полигона на величину отступа, `\` — разность множеств.

### 2.7 Дороги, вода, рельсы, деревья (Шаг 1.7) — реализовано

Код: `geo/src/topology_geo/geometry/{roads,water,rail,vegetation}.py`. Тесты:
`geo/tests/test_geometry_environment.py` (21 тест). Подробности по воде —
`docs/water.md`.

```
ribbon(line, width) = ⋃ line.buffer(width/2, cap="flat")     [дороги, ручьи, балласт ж/д]
level_z(area)       = min(relief(p) for p in ∂area)           [урез КОМПАКТНОГО водоёма — та же формула, что z_base зданий §2.5]
level_fn(x, y)      = interp(profile, line.project(x, y))     [урез ВЫТЯНУТОГО водоёма/русла — см. ниже]
```

Ширина дороги — `tag(width)` (confidence "факт") или таблица по классу
`highway=*` (`WIDTH_BY_HIGHWAY_CLASS`, confidence "умолчание"). Деревья:
одиночные точки (`natural=tree`) с породой из тега или дефолтом; массивы
(`natural=wood`, `landuse=forest|grass`) — расстановка методом отбраковки
(точка в bounding box принимается, если попадает в полигон) с плотностью
`density_per_ha` (по умолчанию 400/га), детерминированная при фиксированном
`seed` (см. тест на воспроизводимость). Проверено точной геометрией: площадь
ленты прямой линии равна `length × width` (buffer с плоскими торцами даёт
ровно прямоугольник, без допуска).

Вода — контур (полигон озера, ось русла) сначала сглаживается методом
Чайкина (срезание углов; у русла концы линии не трогаются — иначе слияние
рек в одном узле OSM разошлось бы). Уровень воды — не всегда единый `min`:
для КОМПАКТНОГО водоёма (соотношение сторон охватывающего прямоугольника
< `WATER_AREA_ELONGATION_RATIO=3.0`) единый минимум физически верен
(поверхность воды плоская); для ВЫТЯНУТОГО — `level_fn` берёт сглаженный
продольный профиль вдоль длинной оси (`relief.tin.build_profile_elevation_fn`,
та же формула §2.4, что и у продольного профиля дороги) — иначе единый
минимум «роет траншею» на одном конце водоёма/русла, лежащего на склоне;
существенно для полномасштабных водных объектов (Этап 2), на маленьком
тестовом пруду разница не проявляется.

### 2.8 Сборка IFC: полигон → меш, объём призмы (Шаг 1.8) — реализовано

Код: `geo/src/topology_geo/ifc/assemble.py`. Тесты:
`geo/tests/test_ifc_assemble.py` (29 тестов). Подробности по дорожному
покрытию — `docs/pavement.md`.

Дорожное покрытие (лента дороги, полоса/тротуар, площадка перекрёстка,
разметка) обязано быть строго ВЫШЕ рельефа, не вровень с ним:

```
z_pavement(x, y) = terrain_z(x, y) + PAVEMENT_CLEARANCE_M      [0.03 м]
z_marking(x, y)  = z_pavement(x, y) + MARKING_CLEARANCE_M      [+0.005 м, поверх покрытия]
```

Вровень с рельефом означало бы гарантированный z-fighting в вебвьюере (Шаг
1.9) и, при малейшем расхождении между независимо построенными сетками
ленты/полосы и TIN (разная плотность вершин), видимое проваливание полотна
под рельеф. Заодно найден и исправлен реальный баг: `SiteTin.interpolate_z`
вне выпуклой оболочки TIN отдавал `None`, единственный вызывающий код
подставлял абсолютный `Z=0` — угол покрытия на реальной отметке рельефа
(например, 150 м) рисовался «под землёй» на всю высоту рельефа, а не
проваливался на сантиметры. Исправлено — экстраполяция отметкой ближайшей
вершины TIN (`scipy.spatial.KDTree`).

Триангуляция контура (возможно, невыпуклого, возможно, с отверстиями) —
`mapbox_earcut` (у `shapely` нет триангуляции, ограниченной контуром
полигона). Экструзия здания — призма: низ на `z_base` (§2.5), верх на
`z_base + height` (§2.5), стены — по ВСЕМ кольцам контура (внешнему и
внутренним/дворам), а не только по внешнему:

```
V = (1/6) · Σ_triangles  v0 · (v1 × v2)      [объём замкнутого меша, теорема о дивергенции]
```

Реальная находка при разработке: первая версия строила стены только по
внешнему кольцу («упрощённо» показалось достаточным для двора) — расчёт
объёма по этой формуле для здания с двором дал 4544 м³ вместо ожидаемых
4032 м³ (= `footprint.area × height`, где `footprint.area` уже учитывает
вычет двора у `shapely`): меш не был замкнут, был как труба без крышки
через двор. После добавления стен по всем кольцам объём совпал с
`footprint.area × height` с точностью до 1e-9 на квадрате, Г-образном
(невыпуклом) контуре и контуре с двором — тест
`test_extrude_polygon_mesh_volume_matches_footprint_area_times_height`
(параметризован тремя случаями) плюс `test_extrude_polygon_mesh_is_watertight_manifold`
(каждое ребро встречается ровно в двух треугольниках, в противоположных
направлениях — необходимое условие замкнутости).

Схема IFC (Шаг 0.2, приём совместимости): `IfcRoad` нативно в IFC4X3
(`IfcSpatialElement`, роднится с `IfcSite` через `aggregate.assign_object`,
как и сам сайт с проектом); в IFC4 схема класс не знает — используется
`IfcBuildingElementProxy` (обычный `IfcElement`, через
`spatial.assign_container`) с пометкой в `Pset_Контекст.Заменяет_класс`.
Реестр `osm_id → GlobalId` (`geo/src/topology_geo/ifc/registry.py`,
таблица `ifc_globalid_registry`, PostGIS) — по одной записи на каждый
исходный объект слоёв 1.5-1.7, независимо от схемы, с `UPSERT` при
пересборке модели с теми же исходными объектами (без дублей строк).

### 2.10 Формы крыш зданий (Шаг 2.2) — реализовано

Код: `geo/src/topology_geo/geometry/roofs.py`. Тесты:
`geo/tests/test_geometry_roofs.py` (25 тестов), `geo/tests/test_pipeline_roof_shape.py`
(сквозной прогон реального `roof:shape=gabled` через весь конвейер).

Геометрические соглашения — не изобретены, а взяты из практики реальных
рендереров OSM-3D (OSM2World и совместимых, спецификация
`Simple3DBuildingsV1` на вики OpenStreetMap, проверено запросом к вики
при разработке, не по памяти):

- `height` — ПОЛНАЯ высота здания (до конька/шатра); высота стен (карниз)
  `eave = height - roof:height`.
- Не прямоугольные контуры: крыша (и при скатной форме — вся геометрия
  здания целиком, стены тоже) строится по ориентированному минимальному
  прямоугольнику контура (OBBox, `shapely.minimum_rotated_rectangle`) — тот
  же приём, что у реальных рендереров; для прямоугольных зданий разница с
  исходным контуром незаметна, для сильно непрямоугольных — упрощение
  силуэта той же природы, что и у реальных рендереров.
- `roof:direction` — направление ската ВНИЗ (от конька к карнизу), не
  направление конька (вики: «viewing direction from high (ridge) to low
  (eaves)»); конёк перпендикулярен этому направлению.
- `roof:orientation=along` (по умолчанию) — конёк вдоль длинной стороны
  OBBox, `=across` — вдоль короткой. Для вальмовой/шатровой крыши конёк
  всегда вдоль длинной стороны (не варьируется) — иначе «съедаемое» вальмами
  измерение могло бы оказаться длиннее сохраняемого (геометрически
  некорректно).

Объёмы всех форм проверены точными замкнутыми формулами (не приближённо, не
«на глаз») — производные интегрированием площади поперечного сечения:

```
двускатная/односкатная:  V = 0.5 · поперечник · высота_конька · длина_конька
                          (одна и та же формула для обеих форм - сечение,
                          перпендикулярное скату, треугольник той же площади,
                          симметричный для двускатной, несимметричный для
                          односкатной)

вальмовая (L ≥ W):       V = h · (L·W/2 - W²/6)
                          (при L=W вырождается в объём пирамиды L²h/3 -
                          согласованность проверена тестом)

шатровая:                V = L · W · h / 3
                          (объём пирамиды над четырёхугольным основанием,
                          для любых L, W - не только квадрата)
```

Замкнутость меша (нет самопересечений/дыр) проверена подсчётом рёбер: каждое
ориентированное ребро должно встречаться ровно в двух гранях, в
противоположных направлениях (тот же приём, что у Шага 1.8).

### 2.11 Составные здания и входы (Шаг 2.2, п. 1 и 3) — реализовано

Код: `geo/src/topology_geo/geometry/buildings.py` (`extrude_buildings`,
`_match_entrances`). Тесты: `geo/tests/test_geometry_buildings.py`,
`geo/tests/test_osm_import_style.py`,
`geo/tests/test_pipeline_building_parts_and_entrances.py` (сквозной прогон).

`building:part=*` — не расчёт, а правило отбора геометрии, пространственное,
не по ссылке (OSM её не даёт):

```
has_part(outline) = ∃ part ∈ building_parts: outline.footprint ∩ part.footprint ≠ ∅

extrude(outline)  = ∅              , если has_part(outline)      [пропущен - см. ниже]
                  = prism(outline) , иначе                        [как в §2.5/§2.10]

extrude(part)     = prism(part)    для каждой part ∈ building_parts  [всегда]
```

Правило «контур, пересекающий хотя бы одну часть, целиком пропускается» — не
самодельное упрощение, а прямая цитата вики (Key:building:part, проверено
запросом при разработке): «the building=\* area might not get rendered by
some 3D-renderers if building:part=\* is used anywhere in the building».
Каждая часть — независимый вход в тот же водопад высоты/крыши (§2.5/§2.10),
своя высота, своя крыша.

`entrance=*` — привязка точки к зданию/части без новой геометрии:

```
entrances(solid) = { e ∈ entrance_points : dist(e, solid.footprint) ≤ 1 м }
```

Буфер 1 м — допуск на неточность привязки узла входа к контуру стены (узел
обычно лежит точно на ребре контура, но реальная OSM-съёмка не идеальна).
Записывается в `Pset_Здание` (`Входов_всего`, `Вход_N_Тип`, `Вход_N_X_м`,
`Вход_N_Y_м`), не как отдельная геометрия — план ограничивает объём этого
пункта метаданными.

### 2.12 Дороги по полосам через osm2streets (Шаг 2.3, п. 1-5) — реализовано

Код: `geo/src/topology_geo/osm/raw_roads.py`, `geo/src/topology_geo/geometry/streets.py`,
`geo/osm2streets/`, `geo/src/topology_geo/ifc/assemble.py` (`_combine_meshes`).
Тесты: `geo/tests/test_osm_raw_roads.py`, `geo/tests/test_geometry_streets.py`,
`geo/tests/test_pipeline_streets.py` (сквозной прогон). Подробное объяснение
решения — `docs/streets.md`.

Сама геометрия полос и разметки (ширина проезжей части/тротуара, положение
относительно оси, площадки перекрёстков, штрихи центральной линии и стрелки
поворота из `turn:lanes`) — не формула этого проекта, а выход реального
инструмента osm2streets (A/B Street); здесь только расчёты до и после
вызова:

**Восстановление связности узлов** (без него osm2streets не видит
перекрёстки, `osm2pgsql`, Шаг 1.1, её не хранит):

```
osm_roads.nodes[i] = ID i-й вершины geom (сохранено при импорте, style.lua)

build_osm_xml(roads) = <node> на каждый уникальный ID узла (первое
                        попавшееся (lon, lat) для этого ID) +
                        <way> с исходными tags на каждую дорогу,
                        <nd ref=...> в порядке nodes
```

Общий ID узла на нескольких `<way>` — топологический перекрёсток; узлы
объявляются раньше всех way (порядок, ожидаемый большинством OSM-парсеров,
тот же приём, что синтетические `.osm`-фикстуры Шага 1.1).

**Clip-полигон буфера** (граница, в которой osm2streets строит сеть) —
окружность в WGS-84, точная, не наивный градусный отступ:

```
circle_wgs84(lon, lat, r) = { msk59_to_wgs84(p) : p ∈ Point(wgs84_to_msk59(lon, lat)).buffer(r) }
```

Тот же принцип точности, что и `clip.py`/`jobs.steps._wgs84_bbox_for_radius`
(буферизация в метрах МСК-59, а не в градусах, которые искажаются с
широтой). Результат osm2streets (GeoJSON, WGS-84) репроецируется обратно
в МСК-59 и локальные координаты участка той же цепочкой, что остальные
слои (`transform_geometry_to_msk59` → `clip_and_localize`, Шаг 1.4).

Инструмент существует только как Rust/WASM (`osm2streets-js`) — вызывается
отдельным процессом Node.js (`geo/osm2streets/convert.mjs`), тем же приёмом,
что системный `osm2pgsql`. Честный водопад (как `NullOvertureSource`,
§2.5): если `node`/пакет недоступны в окружении (`is_osm2streets_available`),
участок остаётся с одной лентой на дорогу (§2.7, `RoadRibbon`), не падает.

**Починка невалидной геометрии разметки** (`make_valid`, перед пересечением
с кругом буфера): среди тысяч мелких полигонов разметки (штрихи центральной
линии через каждые несколько метров, стрелки поворота) на реальных данных
попадаются самопересекающиеся «бабочки» околонулевой площади — та же
природа проблемы, что у `repair_footprint` для контуров зданий (§2.5), без
починки `shapely.intersection` падает с `TopologyException`.

**Слияние мешей одного вида разметки** (`_combine_meshes`, `ifc/assemble.py`):
у одного перекрёстка сотни отдельных штрихов/стрелок; строить по одному
`IfcBuildingElementProxy` на каждый раздуло бы `site.ifc` на реальном радиусе
3 км до многих тысяч тривиальных объектов. К тому же `ifcopenshell.api.geometry.
add_mesh_representation` физически не поддерживает несколько представлений
разного размера в одном продукте (внутри — `numpy.array`, требует
прямоугольной формы, то есть одинакового числа вершин у всех items). Решение —
не бороться с этим ограничением, а склеить геометрию заранее: вершины всех
элементов одного вида (`center line`/`lane arrow`) конкатенируются, грани
сдвигаются на накопленное смещение индексов (тот же приём, что уже
использует `extrude_polygon_mesh` для стен+крыши+дна одной призмы), и в IFC
попадает один продукт на вид разметки с одним меша-представлением, где
каждый штрих — свой непересекающийся кусок треугольной сетки.

**Бордюр** (Шаг 2.3, п. 2, `_build_curb_strips`): osm2streets не выделяет
бордюр отдельным типом полосы (проверено эмпирически на наборе тегов с
`parking`/`cycleway`/`sidewalk`/`shoulder`); строится по границе уже готовых
полос, а не по эвристике/константному смещению — так он остаётся точным при
любой форме полос, которые уже посчитал инструмент:

```
D = ⋃ {полигон полосы : тип = Driving}     (объединение по одной дороге)
S = ⋃ {полигон полосы : тип = Sidewalk}

curb = buffer(∂D ∩ ∂S, w/2, cap="flat"),   w = 0.15 м (по плану, Шаг 2.3, п. 2)
```

Нет бордюра, если `D` или `S` пусты (нечего разделять — например, дорога без
тротуара), либо `surface` дороги — грунтовый (`UNPAVED_SURFACES`: unpaved,
compacted, fine_gravel, gravel, shells, rock, pebblestone, ground, dirt,
earth, mud, laterite, grass, sand, woodchips, snow, ice, salt — вики
Key:surface, раздел Unpaved, проверено запросом при разработке; Шаг 2.3,
п. 4: «грунтовые дороги — без бордюров»). Площадка перекрёстка в `D`/`S` не
входит — бордюр строится только вдоль самой дороги, не вокруг перекрёстка
(упрощение этого прохода).

**Разделитель и газон** (Шаг 2.3, п. 2, `LANE_TYPE_GRASS_VERGE`): в отличие
от бордюра, эти два osm2streets отдаёт сам, отдельными типами полосы, без
геометрического синтеза на Python — `SharedLeftTurn` (полоса разворота/
поворота налево посередине дороги, реальный разделитель встречных потоков)
из тегов `lanes:both_ways=1`+`turn:lanes:both_ways=left`; `Buffer(Verge)`
(газон) из `cycleway:<сторона>:separation:<сторона>=grass_verge` (оба
проверены эмпирически прямым вызовом `osm2streets-js`). Оба типа проходят
через общий код полос без отдельной ветки геометрии — единственная формула
здесь не про форму, а про покрытие:

```
surface(лента) = "grass",                          если тип = Buffer(Verge)
surface(лента) = surface_of(way_ids, tags_by_way),  иначе (как у любой полосы)
```

Газон физически трава, а не асфальт/плитка проезжей части — тег дороги ему
не наследуется (`_surface_for_lane`), в отличие от `SharedLeftTurn` (та же
проезжая часть, тот же асфальт — обычная передача тега).

**Покрытие** (Шаг 2.3, п. 4, `_surface_of`/`_surface_for_lane`): не расчёт, а перенос тега
`surface=*` исходной дороги на каждую её полосу как есть (`Pset_Полоса.
Покрытие`) — тот же принцип, что уже применяется к `Pset_Дорога.Покрытие`
(§2.7), с одним исключением (газон, см. выше). У бордюра (Curb) покрытия нет
— это не тег, а синтезированный элемент. Если несколько way сливаются
osm2streets в одну полосу (степень общего узла = 2, не настоящий
перекрёсток — проверено эмпирически), берётся покрытие первого найденного
way; вторая половина сохранившегося тега теряется — известное ограничение
этого прохода. «Колея» на грунтовых дорогах (тоже п. 4) — геометрическая
деталь профиля, не реализована (нужна Z-вариация внутри ширины полосы,
естественно рассматривать вместе с п. 5).

**Посадка на рельеф с продольным сглаживанием и поперечным уклоном** (Шаг
2.3, п. 5, `ifc/assemble.py`): до этого прохода каждая вершина контура
полосы сэмплировала TIN независимо — без связи с соседними вершинами вдоль
оси и без какого-либо поперечного профиля. Формула — та же техника, что и
продольный профиль дороги в TIN (§2.4) и уровень вытянутого водоёма/русла
(§2.7):

```
axis(polygon)   = long_axis_line(polygon)                    [relief/tin.py — общая утилита, §2.7]
profile(x, y)   = build_profile_elevation_fn(axis, terrain)(x, y)
z_lane(x, y)    = profile(x, y) - LANE_CROSS_SLOPE · dist(point, axis) + PAVEMENT_CLEARANCE_M   [LANE_CROSS_SLOPE = 0.02]
```

Ось — своя у КАЖДОЙ полосы (не общая на дорогу): `LaneRibbon` не хранит
исходную линию проезда osm2streets, только `osm_way_ids` и уже готовый
полигон; на прямом участке оси соседних полос одной дороги почти
параллельны, заметного шва между ними это не даёт. Для почти квадратного
контура (компактная площадка, короткий обрубок полосы) `long_axis_line` не
даёт надёжной оси (соотношение сторон ниже `LANE_ELONGATION_RATIO=1.5`) —
тогда обычная плоская посадка `pavement_elevation_fn` (§2.8), без профиля и
уклона; площадки перекрёстков (`IntersectionArea`) — всегда плоская
посадка, у компактной области без единого направления движения ось
физически не определена. Подробности и все нереализованные части (разметка
на разных лентах на своих осях может слегка разойтись с полосой под ней;
суперэлевация не реализована) — `docs/pavement.md`.

### 2.13 Каркасная и внутриквартальная сеть (Шаг 2.4, п. 1, 4, 5) — реализовано

**Классификация** (п. 1, `geometry/road_network.py`): единая функция для
всех уровней модели дороги (простая лента Шага 1.7 и полоса osm2streets
Шага 2.3):

```
network(highway_class) = "каркасная",         если highway_class ∈ {motorway(_link), trunk(_link),
                                                                       primary(_link), secondary(_link),
                                                                       tertiary(_link)}
                        = "внутриквартальная", иначе (включая unclassified и неизвестные значения)
```

У `RoadRibbon`/`LaneRibbon` есть свой `osm_way_ids`/`highway` — классификация
по тегу напрямую (`_network_of`, `geometry/streets.py`). У `IntersectionArea`/
`LaneMarking` своего `osm_way_ids` нет (перекрёсток/штрих не привязаны к
одному way) — классифицируются геометрически, по факту касания уже
классифицированной каркасной полосы:

```
backbone_union   = ⋃ {lane.polygon : lane.network = "каркасная"}
network(feature) = "каркасная", если feature.polygon ∩ backbone_union ≠ ∅
                  = "внутриквартальная", иначе
```

**Два файла дорог** (п. 4, `ifc/assemble.py`, `jobs/steps.py`): вместо
пересчёта геометрии `build_site_ifc` получает необязательный
`road_network_filter ∈ {None, "каркасная", "внутриквартальная"}` —

```
road_network_filter = None:  все объекты (как раньше, полный site.ifc)
road_network_filter = N:     дороги/полосы/перекрёстки/разметка с network = N,
                              БЕЗ зданий/воды/ж-д/деревьев И БЕЗ рельефа (TIN)
```

Рельеф исключён из обоих отфильтрованных файлов сознательно, не просто «не
относится ни к одной сети»: его меш на честном шаге сетки 1 м (Шаг 1.5) —
самая тяжёлая по памяти часть сборки IFC (сотни тысяч вершин на средний
радиус). Первая версия этого прохода держала TIN в обеих сетях как «общую
привязку» — при разработке это реально привело к OOM на сквозном прогоне
(`test_api.py::test_full_happy_path_creates_downloadable_files`): меш
пересобирался 6 раз за задачу вместо 2 (комбинированный × 2 схемы +
backbone/internal × 2 схемы). Полосы/дороги в отфильтрованном файле уже
несут свою абсолютную высоту (посадка на рельеф, п. 5 выше) — сам меш
террейна для их корректного отображения не нужен, только для визуальной
привязки, а она есть в комбинированном `site.ifc`. Честно: это реальная
и стоящая находка, но САМ OOM на этом конкретном сквозном тесте она не
сняла — сравнение `git stash` показало, что тот же процесс падает по той
же причине (упирается в потолок памяти контейнера ~15 ГБ) и на коде ДО
Шага 2.4, то есть это предсуществующее ограничение среды разработки
(реальный `osm2pgsql` + рельеф 1 м + сборка IFC + GLB в одном процессе
через Celery-eager), а не регрессия этого прохода.

`jobs.steps.assemble_ifc` вызывает `build_site_ifc` ещё дважды на каждую
схему (backbone/internal), реестр `GlobalId` для них — под отдельным
`model_id` (`{job_id}:roads_backbone`/`{job_id}:roads_internal`), не под
общим `model_id` комбинированной модели: иначе `ON CONFLICT (model_id,
layer, osm_id) DO UPDATE` в `register_global_ids` затёр бы GlobalId
комбинированного `site.ifc` GlobalId'ом того же `(layer, osm_id)` из
меньшего файла — тот же исходный OSM-объект существует как ДВА разных
IFC-объекта (в комбинированном и в отфильтрованном файле), с разными
GlobalId. Каркасная сеть помечена `Pset_Дорога/Полоса.Редактируемый=false`,
внутриквартальная — `true` (буквальное "нередактируемая" из плана, не
только описание в документации).

**Параметрическая внутриквартальная сеть** (п. 5, `geometry/roads.py`):
`RoadRibbon.axis` хранит исходную ось (только для дороги с ОДНИМ цельным
сегментом линии — составная `MultiLineString`-геометрия не имеет
единственной оси для редактирования, `axis=None`). Перестройка:

```
rebuild_road_ribbon(road, new_axis):
    отказ, если road.network ≠ "внутриквартальная"   (каркасная нередактируема, п. 4)
    отказ, если road.axis is None                     (нет сохранённой оси)
    ribbon' = new_axis.buffer(road.width_m / 2, cap_style="flat")
    возврат RoadRibbon(..., ribbon=ribbon', axis=new_axis)   [профиль: width_m/surface/highway_class — без изменений]
```

Не реализовано (честно, по факту отсутствия внешних данных, Шаг 0.3):
сверка статуса федеральных/региональных дорог с официальными перечнями
(п. 2) и импорт красных линий ИСОГД (п. 3) — оба требуют внешних
источников, которых нет в этой среде; изобретать значения по догадке было
бы менее честно, чем оставить пункт открытым.

### 2.14 Мосты, путепроводы (Шаг 2.5, п. 1-3) — реализовано

**Обнаружение** (п. 1, `geometry/roads.py`): `is_bridge(raw_tags)` — тег
`bridge=*` истинный, кроме `no` и пустой строки. `build_road_ribbons`
исключает такие участки (строятся отдельно); `osm2pgsql` (Шаг 1.1) уже
сохраняет весь `tags` way как есть, изменений импорта не потребовалось.

**Пролётное строение по оси** (п. 2, `geometry/bridges.py`) — ЛИНЕЙНАЯ, а не
сглаженная (в отличие от §2.4/§2.12), интерполяция между отметками рельефа
только на двух концах оси (устои):

```
z0 = terrain(x0, y0), z1 = terrain(x1, y1)          [x0,y0 / x1,y1 — концы axis]
t(point)  = axis.project(point) / axis.length
z(point)  = z0 + (z1 - z0) · t(point)
```

Рельеф МЕЖДУ устоями на отметку пролёта не влияет вовсе — пролётное
строение жёсткое, это и есть смысл моста (не следовать форме оврага/реки/
дороги под ним). Составная (`MultiLineString`) геометрия не обрабатывается —
нет единственной оси (тот же принцип, что у `RoadRibbon.axis`, §2.13).

**Проверка габарита** (п. 3) — точка проверки это ГЕОМЕТРИЧЕСКОЕ пересечение
оси моста с осью другой (немостовой) дороги (`RoadRibbon.axis`) или пути
(`RailRibbon.axis`, поле добавлено в этом проходе по аналогии с §2.13), не
выборка по площади:

```
для каждой crossing_axis, пересекающей axis моста:
    point = axis.intersection(crossing_axis)
    clearance(point) = deck(point) - terrain(point)

требуемый_минимум = MIN_CLEARANCE_ROAD_M (5,0 м) | MIN_CLEARANCE_RAIL_M (6,0 м)   [норматив по типу пересекаемого объекта]
дефицит = max(0, требуемый_минимум - min(найденные clearance по этому типу))
lift    = max(дефицит по дороге, дефицит по пути, 0)

deck'(point) = deck(point) + lift    [подъём РАВНОМЕРНО по всей длине, не только в точке пересечения]
Статус = "расчётный", если lift > 0, иначе "официальный"
```

Оба норматива — типовые значения по нормам проектирования (дорога — СП
34.13330; путь строже — контактная сеть электрифицированных линий), единые
для всех классов/типов, упрощение, тот же принцип честности, что у
`LANE_CROSS_SLOPE`/`WIDTH_BY_HIGHWAY_CLASS`. Без осей других объектов
(мост через реку/овраг) или без пересечения — проверка не выполняется,
`Pset_Мост.Габарит_м` в файле ОТСУТСТВУЕТ, не подставляется наугад.

**IFC** — `IfcBridge` нативно в IFC4X3, прокси в IFC4 (тот же приём, что
`IfcRoad`, Шаг 0.2); отметка полотна оборачивается ТОЙ ЖЕ `pavement_
elevation_fn` (§2.8/`docs/pavement.md`), что и дорога/полоса — общий зазор
от z-fighting, не отдельная логика. Классификация каркасная/внутриквартальная
(§2.13) применяется и к мосту — участвует в `road_network_filter` (Шаг 2.4,
п. 4) наравне с обычной дорогой.

Не реализовано в этом проходе (честно): опоры по шагу для типа моста и
насыпи подходов (п. 4), тоннели — вырез в рельефе и портал (п. 5, TIN пока
только ДОПОЛНЯЕТСЯ, вычитание объёма нигде в конвейере не реализовывалось);
мост-над-мостом (двухуровневая развязка) не разбирается. Подробности —
`docs/bridges.md`.

### 2.15 Железная дорога и трамвай: ширина насыпи, платформы, переезды, опоры (Шаг 2.6) — реализовано

Код: `geo/src/topology_geo/geometry/rail.py`. Тесты:
`geo/tests/test_geometry_rail.py` (21 тест). Подробности — `docs/rail.md`.

**Ширина насыпи по числу путей и колее** заменяет плоскую константу §2.7
(`BALLAST_WIDTH_M`, одна на все пути):

```
per_track_width  = колея(gauge, мм → м) + 2 · BALLAST_SHOULDER_M   [1,24 м]
ширина_насыпи    = per_track_width + (число_путей(tracks) - 1) · TRACK_SPACING_M   [4,5 м]
```

При умолчаниях (тегов `tracks`/`gauge` нет: 1 путь, колея 1520 мм) формула
даёт ровно прежнее значение §2.7 (4,0 м) — подбор констант намеренный, чтобы
не менять поведение по умолчанию, только объяснить и параметризовать его.
`confidence` = «факт», если хотя бы один из тегов присутствовал и разобрался.

**Платформы** (`railway=platform`, отдельная таблица `osm_railway_platforms` —
общая `osm_railways` типизирована только под линию, полигон/точка в неё не
ложатся): контур берётся как есть, если замкнут; иначе линия буферизуется на
`PLATFORM_LINE_WIDTH_M` (3,0 м). Приподняты над рельефом на
`PLATFORM_HEIGHT_M` (0,3 м, упрощённо).

**Переезды/пешеходные переходы** (`railway=level_crossing`/`crossing`, точки
в новой таблице `osm_railway_crossings`) — упрощённое КВАДРАТНОЕ пятно
разметки со стороной = ширина насыпи БЛИЖАЙШЕГО пути в этой точке (не
восстанавливает геометрию пересекающей дороги — разметка факта переезда).

**Опоры контактной сети**, упрощённо (`electrified` не пусто/не `no`):
регулярный шаг `POLE_SPACING_M` (50 м) вдоль оси, один борт на отступе
`POLE_OFFSET_FROM_AXIS_M` (3,1 м, габарит приближения). Без деления
консоль/портал, без учёта кривизны — честное упрощение.

Собраны в IFC как `IfcBuildingElementProxy`/`Pset_ЖД` (та же схема
совместимости, что у базовой ленты пути — нативный `IfcRail` не задействован,
ошибочная запись об этом в `docs/data-dictionary.md` исправлена в этом
проходе), исключены из `road_network_filter` (§2.13) — не дорожная сеть.

Не реализовано (честно): шпалы/рельсы индивидуальной геометрией «в ближнем
кольце» (нужна интеграция с кольцами LOD, §2.2/Шаг 2.1); дифференциация
колеи по подтипу пути помимо тега `gauge`; чередование бортов опор на
многопутных участках. Подробности — `docs/rail.md`.

### 2.16 Электросети с опорами: провод цепной линией, охранная зона (Шаг 2.7) — реализовано

Код: `geo/src/topology_geo/geometry/power.py`. Тесты:
`geo/tests/test_geometry_power.py` (22), `test_ifc_assemble.py` (11 —
5 на меш-хелперы `mesh_cylinder(radius_top=...)`/`mesh_ribbon_along_path`, 6
на сборку/Pset/фильтр). Подробности — `docs/power.md`.

**Провис провода** (п. 3) — параболическое приближение цепной линии
(стандартный инженерный приём при малом провисе относительно пролёта,
используется в реальном проектировании ВЛ):

```
sag = span_length · SAG_RATIO           [3% длины пролёта, типовое]
z_linear(t) = z0 + (z1 - z0)·t          [t = 0..1 вдоль пролёта]
z(t) = z_linear(t) - sag · 4·t·(1 - t)  [парабола: 0 на концах, -sag на середине]
```

Минимум геометрически на середине пролёта (не смещён к более низкой опоре,
как в физически точной цепной линии при разных отметках концов) —
упрощение. Число проводов — тег `cables` (умолчание 3), разнесены
горизонтальным рядом на `PHASE_SPACING_M` от оси пролёта.

**Геометрия провода в IFC** — не круглая труба, а тонкая ПЛОСКАЯ ЛЕНТА вдоль
сэмплированной 3D-ломаной (`ifc.assemble.mesh_ribbon_along_path`, новый
меш-хелпер этого шага): в каждой точке пути — смещение по горизонтальному
перпендикуляру к локальному направлению на `±width/2`, вертикальная
составляющая (сам провис) в ширину не проецируется. Формула то же, что и у
плоских лент дороги/воды/балласта (`line.buffer(width/2)`), только с
индивидуальной отметкой Z каждой точки пути вместо одной общей плоскости —
проверено аналитически: для прямого горизонтального пути площадь ленты
точно равна `length × width` (`test_mesh_ribbon_along_path_area_matches_
length_times_width_when_flat`).

**Опора/башня** (п. 1) — `mesh_cylinder` получил новый опциональный параметр
`radius_top`: `None` (умолчание, поведение Шагов 0.2/1.7/2.6 не меняется) —
цилиндр постоянного сечения; иначе — конус, сужающийся от `radius` (низ) к
`radius_top` (верх), для решётчатой башни ЛЭП (`power=tower`).

**Расчётная расстановка опор** (п. 2, `place_calculated_poles`) — включается
ТОЛЬКО когда на линии нет НИ ОДНОЙ реальной точки `power=tower/pole` в
пределах `POLE_SNAP_DISTANCE_M`; тогда опоры распределяются РАВНОМЕРНО по
всей длине (шаг = `length / ceil(length / CALCULATED_POLE_SPACING_M)`, без
обрубка последнего пролёта), а не с фиксированным шагом от начала —
проверено (`test_place_calculated_poles_even_spacing_close_to_target`).

**Охранная зона** (п. 5) — буфер вокруг оси линии по РЕАЛЬНОМУ нормативу (ПП
РФ №160 от 24.02.2009), полуширина по классу напряжения от 2 м (до 1 кВ) до
55 м (1150 кВ); без тега `voltage` зона не строится (честный водопад, тот же
принцип, что у проверки габарита моста без осей пересекаемых объектов,
§2.14). `IfcSpatialZone` — `IfcSpatialElement`, роднится с сайтом через
`aggregate.assign_object`, НЕ `spatial.assign_container` (эмпирически
подтверждено: тот падает `AttributeError` на пространственных элементах —
ожидает `ContainedInStructure`, которого у них нет).

**Провод в IFC** — `IfcCableSegment`/`CABLESEGMENT`, НЕ `IfcFlowSegment`
(ранее запланированный в Шаге 0.8): эмпирически через ifcopenshell
подтверждено, что `IfcFlowSegment` не имеет собственного `PredefinedType` ни
в IFC4, ни в IFC4X3 — только у конкретных подтипов; `docs/data-dictionary.md`
исправлен.

Не реализовано (честно): реальные фермы/раскосы башни, бандл-провода,
расчёт провиса по натяжению/температуре/гололёду, сверка охранной зоны с
официальным реестром (НСПД, Шаг 3.1 не реализован). Подробности —
`docs/power.md`.

### 2.17 Библиотека элементов: каталог, ограждения, фонари, PBR-текстуры (Шаг 2.8) — реализовано (частично)

Код: `geo/src/topology_geo/assets/library.py`, `geometry/landscaping.py`.
Тесты: `test_assets_library.py` (16), `test_geometry_landscaping.py` (6),
`test_ifc_assemble.py` (4 новых). Подробности — `docs/asset-library.md`.

**Каталог** (п. 1) — `assets/manifest.json`, запись = категория/тип/LOD/
лицензия/источник/версия/kind∈{generator,texture}/files. Для `kind=
"generator"` — `files` пуст, `source` указывает функцию в репозитории; для
`kind="texture"` — `files` перечисляет реально скачанные файлы,
`license="CC0"`. `resolve_file(entry, filename)` возвращает ПУТЬ к файлу
библиотеки (критерий шага «сцена использует элементы только ссылками») —
не копирует содержимое.

**Ограждение** (п. 2, `geometry.landscaping.build_fences`) — столбы через
типовой пролёт (равномерно по всей длине, тот же приём округления числа
пролётов вверх, что и у расчётной расстановки опор ЛЭП, §2.16) плюс тонкий
поручень (`line.buffer(width/2)`, тот же принцип, что у остальных лент).
`IfcRailing` — предопределённый тип `FENCE` существует ТОЛЬКО в
`IfcRailingTypeEnum` IFC4X3 (эмпирически подтверждено через ifcopenshell);
в IFC4 — `USERDEFINED`, схема-зависимое ветвление по `is_ifc43`, как у
`IfcBridge`/`IfcRoad`, но здесь БЕЗ прокси — класс `IfcRailing` нативен в
обеих схемах, меняется только `PredefinedType`. Стена (`barrier=wall`) —
`IfcWall`, тоже нативно в обеих схемах, точное семантическое соответствие.

**PBR-текстуры** (п. 4) — 5 материалов действия плана (асфальт, плитка,
грунт, газон, бетон), реально скачаны через публичный документированный API
Poly Haven (`api.polyhaven.com` → список активов, `dl.polyhaven.org` →
файлы), CC0. По 3 карты 1К на материал: Diffuse, Normal (`nor_gl`,
OpenGL-конвенция — совпадает с glTF/GLB, куда IFC конвертируется на Шаге
1.9), и упакованный `arm` (AO+Roughness+Metalness, glTF ORM-конвенция,
один файл вместо трёх). Тест читает каждый файл С ДИСКА и проверяет
ненулевой размер — не только присутствие записи в JSON-каталоге.

Не реализовано (честно): готовые licensed 3D-модели деревьев/МАФ/остановок
(п. 3 — принципиально другая задача: поиск+юридическая проверка+интеграция
детальных мешей, а не парсинг документированного текстурного API);
назначение текстур поверхностям в сборке IFC/GLB; отдельная детальная
сетка для рендера помимо упрощённого IFC-тела (п. 5 — этого пайплайна в
проекте вообще пока нет, Этап 4 не достигнут). Подробности —
`docs/asset-library.md`.

### 2.18 Растительность и благоустройство: высота дерева, плотность по типу леса, газон, кустарник, скамейка (Шаг 2.9) — реализовано (частично)

Код: `geo/src/topology_geo/geometry/vegetation.py`,
`geometry/landscaping.py`, `selection/normalize.py`. Тесты:
`test_geometry_environment.py` (+14), `test_geometry_landscaping.py` (+2),
`test_selection_normalize.py` (+3), `test_ifc_assemble.py` (+4).
Подробности — `docs/vegetation.md`.

**Высота дерева** — `height` тег как есть; без тега `DEFAULT_TREE_HEIGHT_M
= 12 м`, независимо от источника породы (`species`/`confidence` — своя
пара полей, `height_m`/`height_confidence` — своя).

**Плотность массива по типу леса**:
```
density(полигон) = FOREST_DENSITY_PER_HA_BY_LEAF_TYPE.get(leaf_type, DEFAULT_FOREST_DENSITY_PER_HA)
                  = {needleleaved: 500, mixed: 400, broadleaved: 350}.get(leaf_type, 400)
```
Типовые иллюстративные значения, не из авторитетного источника
лесоустройства — тот же принцип честности, что и у остальных типовых
констант конвейера.

**Газон отдельно от леса** — до этого шага `landuse=grass` проходил через
ТОТ ЖЕ `scatter_forest_trees`, что и настоящий лес, получая идентичную
плотность 400 дер./га (реальная неточность Шага 1.7, не замеченная до
явной проверки условий фильтра). Исправлено: `scatter_forest_trees`
исключает `landuse=grass` (и `natural=scrub`) явной проверкой тегов;
`build_lawns` — отдельный генератор плоской поверхности без деревьев.

**Кустарник** (`natural=scrub`) — новый тег для импорта (`style.lua`, та же
таблица `osm_vegetation`), `scatter_shrubs` — тот же метод отбраковки
(rejection sampling), что и `scatter_forest_trees`, с параметрами вместо
леса: `SHRUB_HEIGHT_M=1,2 м`, `SHRUB_DENSITY_PER_HA=1500/га` (ниже и гуще
дерева — реалистичное соотношение, не точный расчёт).

**Скамейка** (`amenity=bench`) — упрощённый плоский короб
(`extrude_polygon_mesh` на прямоугольник 1,5×0,5 м, высота 0,45 м), без
ориентации. `IfcFurniture` — нативный класс в обеих схемах (IFC4/IFC4X3),
`IfcFurnitureTypeEnum` не содержит значения `BENCH` ни в одной (эмпирически
подтверждено через ifcopenshell, тот же метод проверки, что и у `IfcRailing
TypeEnum`/`FENCE` в §2.17) → `PredefinedType=USERDEFINED`.

Не реализовано (честно): дифференциация по конкретному виду (`species`)
вместо огрублённого `leaf_type`; ориентация скамейки; готовые детальные
3D-модели растительности/МАФ (тот же пробел, что и у §2.17, п. 3).
Подробности — `docs/vegetation.md`.

### 2.19 Выходные форматы: федеративные IFC-слои, LandXML/CityJSON/DXF, meta.json (Шаг 2.10) — реализовано (частично)

Код: `geo/src/topology_geo/export/{landxml,cityjson,dxf}.py`,
`ifc/assemble.py`, `jobs/steps.py` (федеративные слои + новый шаг
`package_outputs`), `api/app.py`. Тесты: `test_export_landxml.py` (7),
`test_export_cityjson.py` (9), `test_export_dxf.py` (7),
`test_jobs_steps_package_outputs.py` (7), `test_osm_import_log.py` (3).
Подробности — `docs/output-formats.md`.

**Федеративные IFC-слои** (п. 1) — на каждую схему добавлены `relief_*.ifc`/
`buildings_*.ifc`/`power_*.ifc`, тот же приём независимого `SiteModel` +
`build_site_ifc`, что и `roads_backbone/internal` (§2.13/Шаг 2.4, п. 4):
объекты уже посчитаны один раз выше по функции, файл — просто их
подмножество в отдельном `ifcopenshell.file`. Честно зафиксирован побочный
эффект: `relief_*.ifc` пересобирает TIN-меш в IFC-продукты ЕЩЁ раз на
каждую схему (та же операция, что даёт `terrain` в комбинированном
`site.ifc`) — TIN входит в сборку 4 раза за задачу вместо 2 (роста избегали
именно для `roads_backbone/internal` в Шаге 2.4 по той же причине — здесь
рост принят осознанно, т.к. `relief.ifc` явно требуется примером плана).
`power_*.ifc`/`buildings_*.ifc` своего TIN не несут; для зданий это
безразлично (используют собственную `base_z`), но `_terrain_elevation`
(`ifc/assemble.py`) при `tin is None` возвращает `0.0` — то есть в
ИЗОЛИРОВАННОМ `power_*.ifc` опоры/провода стоят на условной плоскости z=0
(в комбинированном `site.ifc` рельеф есть, высоты верны).

**LandXML** (п. 2, `export/landxml.py`) — LandXML 1.2, вручную через
`xml.etree.ElementTree` (открытая XML-схема). `<Surfaces><Surface>` —
точки/треугольные грани готового TIN (Шаг 1.5), индексация граней с 1
(требование формата). `<Alignments><Alignment>` — по оси (`RoadRibbon.axis`/
`RailRibbon.axis`, Шаг 2.4/2.5, только объекты с ОДНИМ цельным сегментом
линии), исключительно прямые сегменты `<Line>` (данных о радиусе кривой в
конвейере нет — `Curve`/`Spiral` не строятся). Координаты — локальные метры
участка, без формального `<CoordinateSystem>`/EPSG (у МСК-59 в проекте нет
декларированного глобального кода).

**CityJSON** (п. 2, `export/cityjson.py`) — CityJSON 1.1, обычный `dict`.
Одно здание → один `Building` CityObject с LOD0 (плоский контур пятна
застройки на `base_z`, `MultiSurface`, без экструзии), LOD1 (простая призма
на всю высоту, `extrude_polygon_mesh`, форма крыши не учитывается — по
определению LOD1) И LOD2 (та же меш-логика, что IFC-рендер зданий: плоская
крыша → тот же `extrude_polygon_mesh`; скатная → `oriented_bounding_box` +
`build_pitched_building_mesh`) — план явно требует «CityJSON (LOD0-2)».
Каждая треугольная грань меша LOD1/LOD2 — отдельная
`Solid`-поверхность `[[i,j,k]]` (валидно, но многословнее объединённых
плоских полигонов). Вершины — общий список без дедупликации между
зданиями. `transform` тождественный (`scale=[1,1,1]`, без целочисленного
квантования координат). `metadata.referenceSystem` не указывается (та же
причина, что у LandXML).

**DXF** (п. 2, `export/dxf.py`, новая зависимость `ezdxf`) — плоский
2D-чертёж: замкнутые `LWPOLYLINE` (внешний контур + отверстия) по трём
слоям — здания, дороги (контур ленты), вода. Горизонтали рельефа, рельсы,
ЛЭП, растительность, аннотации/легенда — не строятся (явно выбранное
подмножество, не «всё, что есть в IFC»).

**`meta.json` + упаковка** (п. 3, `jobs/steps.py::package_outputs`, новый
последний шаг `DEFAULT_PIPELINE`) — скачивает уже загруженные байты
предыдущих шагов, упаковывает в `jobs/{id}/package.zip`, БЕЗ пересборки
TIN/геометрии. Схема — `schemas/meta.schema.json` (Шаг 0.8, проверено
`jsonschema.validate` в тестах). `sources` — РЕАЛЬНЫЙ журнал:
`osm_import_log` (Шаг 1.1, п. 4, новая функция `all_latest_sources` —
последняя запись КАЖДОГО источника, а не угаданное единственное имя;
лицензия OSM — известная константа ODbL) и `dem_coverage` (Шаг 1.2, п. 4,
по bbox задачи; лицензия рельефа НЕ хранится в реестре покрытия — честно
помечена как не зафиксированная, не придумана). `coordinate_system.
base_point` сохранён в результате `assemble_ifc` (не пересчитывается через
TIN заново). Переименование `roads_internal` (внутренний Storage-ключ Шага
2.4) → `roads_local` (имя итогового файла из `docs/data-dictionary.md` §4)
сделано НА ГРАНИЦЕ упаковки, не в самом `assemble_ifc` — внутренний ключ
шага не тронут (риск задеть стабильный код Шага 2.4 ради чистого
наименования не оправдан).

`api/app.py::get_job_files` расширен: верхнеуровневые ключи `s.result`,
оканчивающиеся на `_storage_key` (не только вложенные в `schemas[schema]`,
как раньше, Шаг 2.4), тоже раскрываются в отдельные файлы — понадобилось
для схема-независимых LandXML/CityJSON/DXF и для `package_outputs`
(`meta_storage_key`/`archive_storage_key`).

Не реализовано (честно): отдельный `vegetation.ifc` (список примеров плана
его не называет); `networks.ifc`/`constraints.ifc` (Шаги 3.1/3.4, Этап 3 не
начат); конвертер в `XKT` (формат упомянут в схеме `meta.json`, но не
производится); реальное открытие LandXML/DXF/CityJSON в целевой CAD/ГИС
программе (критерий проверки шага недоступен AI-сессии без человека).
Подробности — `docs/output-formats.md`.

## 3. Как обновлять этот документ

Каждый шаг плана, который вводит новый расчёт (не просто перекладывание
данных), получает здесь раздел: формула(ы) + ссылка на модуль/тесты + статус
(заготовка/реализовано). Правки вносятся в том же коммите, что и код.
