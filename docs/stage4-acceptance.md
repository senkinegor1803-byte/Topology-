# Приёмка Этапа 4 (Шаг 4.12)

Этап 4 (Шаги 4.1-4.11) — визуализация, рендер, личный кабинет и API. Ключевое
отличие от Этапов 1-3: большинство действий плана рассчитаны на GPU
(Blender Cycles-рендер на видеокарте, Unreal Engine, обучение Gaussian
splatting) и специализированное окружение (Docker с CUDA, реальный
телефон). В этой среде разработки нет GPU (`nvidia-smi` отсутствует) и не
запущен демон Docker — оба факта установлены реальной проверкой, а не
предположением, до начала работы над этапом.

Реальные находки при разработке (не гипотетические, зафиксированы тестами
и/или в коде):
- glTF по спецификации Y-вверх, весь конвейер проекта — Z-вверх: без
  компенсирующего поворота −90° вокруг X здание «ложится на бок» при
  импорте в `bpy` — найдено сравнением ожидаемого/полученного мирового
  ограничивающего объёма на реальном здании (Шаг 4.1), затем
  переиспользовано во всех последующих `bpy`-модулях (4.2/4.5/4.7).
- `obj.rotation_euler` не действует, пока `rotation_mode` объекта —
  `'QUATERNION'` (умолчание импортёра glTF) — нужно явно переключать в
  `'XYZ'` перед поворотом (Шаг 4.1).
- В OpenUSD локальная опись всегда сильнее ссылки (`references`) на тот
  же путь — подстановка библиотечной модели (Шаг 4.1, п. 2) не работает,
  если не убрать локальные геометрические атрибуты примитива явно
  (`Sdf.PrimSpec.RemoveProperty`) перед добавлением ссылки.
- Blender экспортирует вершинные цвета (`COLOR_0`) как нормализованный
  `UNSIGNED_SHORT`, не `FLOAT` — найдено при чтении результата бейка
  освещения напрямую через `pygltflib` (Шаг 4.2).
- Celery/Redis: приоритет 0..9, где 0 — НАИВЫСШИЙ (соглашение AMQP), не
  наоборот — проверено вручную экспериментом с реальным Celery+Redis ДО
  написания продакшен-кода (Шаг 4.5).
- `usd-core` (пакет `pxr`) оказался лучшим выбором для композиции/
  материалов/проверки сцены, чем `bpy`: легче (30 МБ против 374 МБ), не
  требует Blender, позволяет читать структуру сцены напрямую — только
  конвертация GLB→USD (Шаг 4.1) и растровый рендер (Шаги 4.2/4.5/4.7)
  реально нуждаются в `bpy`.

## Личный кабинет и API — реально работающий backend, не заглушка

В отличие от рендер-шагов (где ограничение — отсутствие GPU), Шаги
4.10-4.11 ограничены не средой, а объёмом: это полноценный backend
(авторизация, роли, владение задачами, уведомления, публичные ссылки,
API-ключи, вебхуки, выгрузка в Pilot-BIM через папку обмена), реально
проверенный на настоящем FastAPI+PostgreSQL (71 тест, включая
сквозные — реальный локальный HTTP-сервер получает настоящий вебхук при
падении реальной задачи, реальный запрос ограничений Шага 3.1 по
реальному bbox для гейта «закрытый контур»). Существующие тесты Шага 1.3
(`test_api.py`) перепроверены без регрессий после добавления авторизации
поверх ранее полностью анонимного API.

## Честно не выполнено (критерии раздела плана)

- **«Комплект 8 ракурсов + видео + 3 панорамы ≤ 1 ч без участия
  человека»** (критерий Шага 4.12) — логика полностью реализована
  (`camera_shots.bird_eye_cameras` даёт 4 ракурса, `pedestrian_view_points`
  — оставшиеся, `flythrough_path`+`panorama.render_flythrough_video` —
  видео, `panorama.render_panorama` — панорамы), но реальное время «≤ 1 ч»
  — GPU-критерий: CPU Cycles-рендер того же кадра на порядки медленнее,
  измерять и заявлять как «подтверждено» время без GPU означало бы
  выдавать несопоставимое число за GPU-оценку — намеренно не сделано.
- **«Презентационный вид работает на телефоне»** (Шаг 4.2/4.12) — нет
  реального телефона в этой среде, только адаптивная вёрстка и
  headless-браузер той же вёрстки (тот же класс ограничения, что и Шаг
  1.9).
- **«Кабинет и API приняты»** (Шаг 4.12) — приёмка подразумевает
  решение человека (владельца продукта/BIM-специалиста), не
  автоматическую проверку; backend полностью реализован и протестирован,
  но формальной приёмки не было и не может быть в рамках AI-сессии.
- **Docker-образ Blender с GPU** (Шаг 4.5, п. 1) — `infra/render-
  worker.Dockerfile` написан и синтаксически провалидирован
  (`docker compose config`), но не собран и не запущен: в этой среде нет
  GPU и не поднят демон Docker (`docker info` не достаёт до
  `/var/run/docker.sock`).
- **Unreal Engine / доводка нейросетью / Gaussian splatting** (Шаги
  4.6/4.8/4.9, все помечены «опция» в самом плане) — честный отказ без
  кода: проприетарный движок (не `pip install`) и два GPU-инференс/
  обучение сценария, недоступных в этой среде.

## Известные архитектурные пробелы, честно перенесённые дальше

- Отбор именно LOD2-тайлов (Шаг 2.1) для запекания освещения (Шаг 4.2) —
  функция `lightmap_bake.bake_lighting_to_vertex_colors` запекает ЛЮБОЙ
  переданный ей `.glb`; встраивание вызова в конвейер генерации тайлов —
  отдельная интеграционная работа.
- «Проекты» личного кабинета (Шаг 4.10, `GET /projects`) не сводят
  версии/ЖК/запросы ТУ/рендеры одной задачи в единый ответ — данные
  Шагов 3.6-3.12 и 4.5 не хранят `job_id` в своих текущих схемах.
- Детальные библиотечные модели для подстановки (Шаг 4.1, п. 2: деревья,
  МАФ, остановки) — каталог библиотеки (Шаг 2.8) расширен под них
  (`kind="model"`), но реальных лицензированных моделей по-прежнему нет
  (тот же пробел, что был честно зафиксирован в Шаге 2.8).
- Отдельного фронтенда личного кабинета (SPA/страница, аналог
  `web/viewer`/`web/panorama`) нет — только backend API; критерий «путь
  за 30 минут без инструкции» требует интерфейса и живого пользователя.

## Итог

Кодовая часть Этапа 4 сделана и реально протестирована в объёме,
доступном без GPU, реального телефона, лицензии Pilot-BIM и участия
человека для формальной приёмки — статус ✅(частично), тот же принцип,
что у Этапов 1-3. Все GPU-зависимые шаги (4.1/4.2/4.5/4.7) реализованы
и проверены на CPU-эквиваленте их логики (`bpy` Cycles CPU-бэкенд,
`pxr` для композиции/материалов) — не имитацией, настоящим рендером
меньшего масштаба; не проверены только количественные GPU-критерии
производительности. Шаги 4.10/4.11 (личный кабинет и внешний API) не
имеют GPU-ограничения вовсе и реализованы в полном объёме, доступном
без внешнего фронтенда и реальных учётных данных Pilot-BIM. Полное
закрытие этапа требует действий вне AI-сессии: реального GPU-хоста
(тесты производительности рендера, сборка/прогон Docker-образа),
реального телефона, лицензии/доступа к Pilot-BIM API, фронтенда личного
кабинета и формальной приёмки человеком.
