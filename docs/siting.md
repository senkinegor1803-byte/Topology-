# Посадка ЖК на участок (Шаги 3.6-3.9)

Реализация: `geo/src/topology_geo/siting/`. Первый раздел проекта, где
появляется понятие «конкретный участок» (полигон) — все задачи Этапов 1-2
оперируют круглой зоной радиуса от центра, не полигоном.

## Приём и привязка ЖК (Шаг 3.6)

`siting/building_placement.py`.

**Чтение геопривязки** (п. 1) — `read_map_conversion(model)`: `IfcMap
Conversion` (тот же механизм IFC4/IFC4X3, которым сам проект пишет
геопривязку своих моделей, Шаг 0.4/1.8 — `ifc.generate_test_ifc`/`ifc.
assemble`), не специальный парсер под конкретный экспортёр — Renga
использует штатный механизм схемы. Реально проверено круговым тестом:
собран реальный IFC через `ifcopenshell.api` с `IfcMapConversion`
(эталонные Eastings/Northings/высота/поворот 30°), прочитан обратно —
все значения совпали, включая угол поворота через `atan2(XAxisOrdinate,
XAxisAbscissa)`. Без `IfcMapConversion` — честный `None`, не выдуманные
нулевые координаты.

**Мастер размещения** (п. 2, если привязки нет) —
`place_building_manually(footprint_local, origin_x_m, origin_y_m,
rotation_deg, site_boundary)`: поворот вокруг локального начала координат
+ перенос в точку на карте, затем проверка — контур ЖК ПОЛНОСТЬЮ внутри
границы участка (`is_within_site`) и доля площади, попавшей внутрь
(`overlap_ratio`, для случая частичного выхода за границу). Оба контура —
`footprint_local` и `site_boundary` — должны быть в ОДНОЙ метрической
системе координат (например, МСК-59 — перевод из WGS-84 делает вызывающая
сторона через уже существующий `coords.transform_geometry_to_msk59`, Шаг
0.4, как и весь остальной проект).

**Пятно застройки по секциям** (п. 3) — `building_footprints_by_
building(model)`: IFC не имеет стандартного класса «секция» — в реальных
проектах секция ЖК обычно оформляется отдельным `IfcBuilding` (несколько
корпусов/секций в одном файле), поэтому пятно строится НА КАЖДЫЙ
`IfcBuilding` отдельно, обход по реальным связям схемы
(`IfcRelContainedInSpatialStructure`/`IfcRelAggregates`), не через
`ifcopenshell.util.element` (чьё поведение на граничных случаях —
элемент напрямую в `IfcSite` без этажа — не гарантировано документированным
способом без выхода в сеть за актуальной документацией библиотеки). Пятно
— выпуклая оболочка (convex hull) всех точек геометрии элементов здания в
плане — честное упрощение: точный контур требовал бы объединения (union)
всех отдельных footprint'ов, что при упрощённых/пересекающихся телах
модели не всегда даёт единый простой полигон, а выпуклая оболочка — всегда.

6 новых тестов (`test_siting_building_placement.py`), включая полный
цикл запись→чтение реального IFC с двумя `IfcBuilding`.

## Отметка 0.000 и вертикальная планировка (Шаг 3.7)

`siting/vertical_planning.py` — переиспользует инфраструктуру рельефа Шага
1.2 (`relief.tin.sample_bilinear`, `relief.merge.merge_with_transition`),
не строит параллельную: вертикальная планировка — та же задача «слить
новую поверхность со старой с плавным переходом», что и слияние источников
рельефа, только источник теперь не другой DEM, а проектная площадка.

**0.000** (п. 1, вариант «расчётом по рельефу у входов») —
`design_elevation_from_entrances`: среднее фактического рельефа в точках
входов (не мин/макс — среднее минимизирует суммарный перепад со всеми
входами сразу при нескольких входах на разных высотах).

**Откосы/подпорные стенки** (п. 2) — `check_retaining_wall_needed`:
уклон отвала 1:1,5 (СП 45.13330.2017, типовое представительное значение
для нескальных грунтов); если требуемое заложение (`|перепад| × 1,5`)
превышает разумный запас места — честный флаг «нужна подпорная стенка»
вместо тихого построения нереалистично пологого/крутого откоса.

**Объёмы выемки/насыпи** (п. 3) — `compute_cut_fill_volumes`: численное
интегрирование по пикселям СЕТКИ РЕЛЬЕФА (та же сетка, что несёт остальной
проект, не отдельная грубая дискретизация) — `выемка` там, где факт выше
проекта, `насыпь` — где ниже.

**Обновление рельефа в зоне участка** (п. 4) — `update_relief_in_site_
zone`: буквально `merge_with_transition(base=текущий_рельеф, overlay=
проектная_отметка, ...)` — ширина перехода по умолчанию берётся из
реального заложения откоса при максимальном перепаде вокруг площадки
(`check_retaining_wall_needed`), не произвольное число. Реально
протестировано: маленькая площадка с перепадом БОЛЬШЕ её размера честно
не успевает дойти до проектной отметки уже в центре (смешанное значение)
— это ожидаемое поведение линейного сглаживания, а не ошибка (тест
`test_update_relief_in_site_zone_large_step_gives_wide_transition`
специально это фиксирует, не прячет).

8 новых тестов (`test_siting_vertical_planning.py`).

**Честно не реализовано:** реальная геометрия подпорной стенки (вертикальная
грань конструкции) — только честный булев флаг «нужна» вместо тихого
некорректного пологого перехода; критерий шага («объёмы сходятся с расчётом
в КРЕДО или вручную в пределах 5%») не проверен — нужны реальные
контрольные цифры пилота (Шаг 0.1).

## Очистка площадки и подъезды (Шаг 3.8)

`siting/site_access.py`. `clear_site(features, footprint)` — реальный
список удалённых объектов (не только счётчик — Шаг 3.9 сможет перечислить
их в отчёте посадки). `build_access_road(site_boundary, roads, obstacles)`
— ближайшая дорога (любой сети) через `shapely.ops.nearest_points`
(честный кратчайший путь между границей участка и дорогой — для «подъезда»,
короткого локального примыкания, это не эвристика, а точный ответ);
примыкание к КАРКАСНОЙ сети (`geometry.road_network.NETWORK_BACKBONE`,
Шаг 2.4) помечается `requires_user_confirmation=True` — буквально действие
плана «только с подтверждением пользователя» (сама подача такого
подтверждения — интерфейс, не реализован, но честный флаг для него есть).
Пересечение с препятствиями (зданиями/запретными зонами) — прямая проверка
геометрии пути.

6 новых тестов. Честно не реализовано: сам интерфейс подтверждения
пользователем; критерий шага («на 3 тестах подъезд построен без пересечения
зданий и зон запрета») не проверен — нужны реальные тестовые участки
(Шаг 0.1).

## Проверки и отчёт посадки (Шаг 3.9)

`siting/{checks,bcf_export,pdf_report}.py`.

**Проверки** (п. 1) — `run_all_checks`: огибающая застройки (Шаг 3.3, п. 2:
здание ЦЕЛИКОМ внутри огибающей), зоны ограничения (Шаг 3.1/3.2: одна
универсальная проверка пересечения на универсальной таблице зон —
красные линии/ЗОУИТ/ЛЭП различаются только `zone_type`, не тремя копиями
одной функции), сети — горизонтальное расстояние до сегментов Шага 3.4
меньше норматива. ВЕРТИКАЛЬНОЕ расстояние до сетей и упрощённая инсоляция
ЧЕСТНО не реализованы: у здания в этой модели нет глубины заложения
фундамента (посадка ЖК строит только пятно в плане, не фундамент), а
инсоляция требует модели солнца/теней Шага 4.3, которой в проекте ещё нет
(тот же отказ, что уже зафиксирован для неё в Шаге 3.3).

**BCF** (п. 2) — `build_bcf`: реальный BIM Collaboration Format
(buildingSMART, тот самый формат, который план называет напрямую — «BCF
открывается в Renga или Pilot-BIM»), не изобретённый формат — zip-архив,
подкаталог на GUID-тему коллизии, `markup.bcf` (заголовок/описание) +
`viewpoint.bcfv` (ссылки на объекты по `IfcGuid`). Снимок вида ЧЕСТНО не
генерируется — потребовал бы headless-рендер сцены (текущий рендер —
three.js в браузере, Шаг 1.9, не подключён к Python-бэкенду); содержательная
часть коллизии (тема + ссылки на объекты, которые Renga/Pilot-BIM
использует для «перехода к объектам», критерий шага) реализована полностью
и реально проверена обратным разбором (`zipfile`+`ElementTree`, не только
«не упало»).

**PDF-отчёт** (п. 3) — `build_placement_report_pdf` (новая зависимость
`reportlab`): разделы буквально по действию плана — схема посадки (сведена
к текстовому описанию контура, не векторный чертёж, см. ниже), отметки,
объёмы, таблица коллизий, перечень источников с датами. Реальная находка
при первой же проверке: встроенные шрифты `reportlab` (Helvetica) не знают
кириллицы — текст рендерился пустыми квадратами (`■■■■■`); исправлено
регистрацией системного `DejaVuSans.ttf` (полное покрытие кириллицы) —
проверено обратным разбором текста PDF (`pypdf`, тестовая зависимость), не
только магическим заголовком `%PDF`.

17 новых тестов (`test_siting_checks.py` — 7, `test_siting_bcf_export.py`
— 5, `test_siting_pdf_report.py` — 5).

**Честно не реализовано:** полноценная векторная схема посадки в PDF
(нужен модуль компоновки листа — масштаб/рамка/штамп, которого в проекте
нет нигде); снимки вида в BCF (headless-рендер); вертикальные зазоры до
сетей и инсоляция (см. выше); критерий шага («BCF открывается в Renga...,
все внесённые тестовые коллизии найдены») не проверен без реального
BIM-инструмента и пилота (Шаг 0.1/0.2).

## Честно не реализовано (Шаг 3.6)

- Критерий шага («3 тестовых проекта размещаются с ошибкой ≤0,1 м
  относительно ручной посадки») — не проверен, нужны реальные тестовые
  проекты ЖК из Renga (Шаг 0.1, недоступен AI-сессии).
- Загрузка IFC именно ИЗ Renga (как конкретного инструмента) — функция
  читает штатный механизм IFC-схемы, которым Renga пользуется, но
  специфичные для Renga соглашения/расширения (если есть) не изучены —
  нет доступного образца реального файла Renga в этой среде.
