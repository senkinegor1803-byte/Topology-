# Посадка ЖК на участок (Шаги 3.6-3.9)

Реализация: `geo/src/topology_geo/siting/`. Первый раздел проекта, где
появляется понятие «конкретный участок» (полигон) — все задачи Этапов 1-2
оперируют круглой зоной радиуса от центра, не полигоном.

## Приём и привязка ЖК (Шаг 3.6)

`siting/building_placement.py`.

**Чтение геопривязки** (п. 1) — `read_map_conversion(model)`: `IfcMap
Conversion` (тот же механизм IFC4/IFC4X3, которым сам проект пишет
геопривязку своих моделей, Шаг 0.4/1.8 — `ifc.generate_test_ifc`/`ifc.
assemble`), не специальный парсер под конкретный экспортёр — Renga
использует штатный механизм схемы. Реально проверено круговым тестом:
собран реальный IFC через `ifcopenshell.api` с `IfcMapConversion`
(эталонные Eastings/Northings/высота/поворот 30°), прочитан обратно —
все значения совпали, включая угол поворота через `atan2(XAxisOrdinate,
XAxisAbscissa)`. Без `IfcMapConversion` — честный `None`, не выдуманные
нулевые координаты.

**Мастер размещения** (п. 2, если привязки нет) —
`place_building_manually(footprint_local, origin_x_m, origin_y_m,
rotation_deg, site_boundary)`: поворот вокруг локального начала координат
+ перенос в точку на карте, затем проверка — контур ЖК ПОЛНОСТЬЮ внутри
границы участка (`is_within_site`) и доля площади, попавшей внутрь
(`overlap_ratio`, для случая частичного выхода за границу). Оба контура —
`footprint_local` и `site_boundary` — должны быть в ОДНОЙ метрической
системе координат (например, МСК-59 — перевод из WGS-84 делает вызывающая
сторона через уже существующий `coords.transform_geometry_to_msk59`, Шаг
0.4, как и весь остальной проект).

**Пятно застройки по секциям** (п. 3) — `building_footprints_by_
building(model)`: IFC не имеет стандартного класса «секция» — в реальных
проектах секция ЖК обычно оформляется отдельным `IfcBuilding` (несколько
корпусов/секций в одном файле), поэтому пятно строится НА КАЖДЫЙ
`IfcBuilding` отдельно, обход по реальным связям схемы
(`IfcRelContainedInSpatialStructure`/`IfcRelAggregates`), не через
`ifcopenshell.util.element` (чьё поведение на граничных случаях —
элемент напрямую в `IfcSite` без этажа — не гарантировано документированным
способом без выхода в сеть за актуальной документацией библиотеки). Пятно
— выпуклая оболочка (convex hull) всех точек геометрии элементов здания в
плане — честное упрощение: точный контур требовал бы объединения (union)
всех отдельных footprint'ов, что при упрощённых/пересекающихся телах
модели не всегда даёт единый простой полигон, а выпуклая оболочка — всегда.

6 новых тестов (`test_siting_building_placement.py`), включая полный
цикл запись→чтение реального IFC с двумя `IfcBuilding`.

## Честно не реализовано (Шаг 3.6)

- Критерий шага («3 тестовых проекта размещаются с ошибкой ≤0,1 м
  относительно ручной посадки») — не проверен, нужны реальные тестовые
  проекты ЖК из Renga (Шаг 0.1, недоступен AI-сессии).
- Загрузка IFC именно ИЗ Renga (как конкретного инструмента) — функция
  читает штатный механизм IFC-схемы, которым Renga пользуется, но
  специфичные для Renga соглашения/расширения (если есть) не изучены —
  нет доступного образца реального файла Renga в этой среде.
