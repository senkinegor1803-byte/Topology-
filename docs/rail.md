# Железная дорога и трамвай (Шаг 2.6)

Базовая лента пути с плоской шириной насыпи — Шаг 1.7, п. 3
(`geometry.rail.build_rail_ribbons`). Этот документ — уточнения Шага 2.6:
реальная ширина насыпи по числу путей и колее, платформы, переезды, опоры
контактной сети упрощённо.

## Ширина насыпи по числу путей и колее

Плоская константа Шага 1.7 (`BALLAST_WIDTH_M = 4,0 м`, одна на все пути)
заменена расчётом (`compute_ballast_width_m`):

```
per_track_width = колея + 2 * BALLAST_SHOULDER_M   # обочина с каждой стороны
ширина_насыпи   = per_track_width + (число_путей - 1) * TRACK_SPACING_M
```

| Параметр | Значение | Источник |
| --- | --- | --- |
| `BALLAST_SHOULDER_M` | 1,24 м | подобрано так, чтобы при умолчаниях (1 путь, колея 1520 мм) формула давала ровно прежнее плоское значение Шага 1.7 (4,0 м) — поведение по умолчанию не меняется |
| `TRACK_SPACING_M` | 4,5 м | типовое междупутье на прямых участках (СП 119.13330, диапазон ~4,1-4,5 м), одно значение на все пары путей |
| `DEFAULT_GAUGE_M` | 1,520 м | российская широкая колея; одно значение для rail/tram/light_rail — отдельного справочника колеи по типу пути не ведём |

Тег `tracks=*` — число путей (по умолчанию 1, если отсутствует/некорректен).
Тег `gauge=*` — колея в МИЛЛИМЕТРАХ (стандарт OSM, вики Key:gauge), переводится
в метры. `Pset_ЖД.Источник_ширины` — «факт», если хотя бы один из двух тегов
присутствовал и разобрался, иначе «умолчание» (тот же принцип confidence, что
у `Pset_Дорога.Ширина_м`/`width_confidence` в `geometry.roads`).

Это по-прежнему упрощение: реальное междупутье растёт на кривых, а ширина
насыпи зависит от класса линии/нагрузки — здесь одна формула на все случаи,
честно, без придуманной точности.

## Платформы (`railway=platform`)

В OSM платформа встречается в двух видах: замкнутым контуром (полигон
посадочной зоны) или одной линией вдоль пути (площади не имеет сама по себе).
Общая таблица `osm_railways` определена в `style.lua` с фиксированным типом
геометрии `linestring` — туда не ложится ни полигон, ни точка, поэтому
платформы (и переезды ниже) вынесены в отдельные таблицы:

- `osm_railway_platforms` (`geometry`, полигон ИЛИ линия) — `railway=platform`
  на way; в `process_way` замкнутый контур сохраняется как полигон,
  незамкнутый — как линия (в отличие от `insert_way_geom(as_area=true)`,
  который для незамкнутого way МОЛЧА пропускает объект — здесь оба случая
  нужны, поэтому не переиспользуется как есть).
- `geometry.rail.build_platform_areas` — полигон берётся как есть; линия
  буферизуется на `PLATFORM_LINE_WIDTH_M = 3,0 м` (типовая ширина платформы,
  упрощение).

Платформа приподнята над рельефом на `PLATFORM_HEIGHT_M = 0,3 м` — упрощённо,
без деления на низкую (~0,2 м) и высокую (~0,55 м над УГР) по типу состава.

## Переезды и пешеходные переходы (`railway=level_crossing`/`crossing`)

Точки-узлы — новая ветка `process_node` в `style.lua` (в существующем стиле
`railway=*` на узлах вообще не обрабатывался), отдельная таблица
`osm_railway_crossings` (`point`).

`geometry.rail.build_level_crossings` представляет переезд упрощённым
КВАДРАТНЫМ пятном разметки со стороной, равной ширине насыпи БЛИЖАЙШЕГО пути
в этой точке (`RailRibbon.width_m` уже посчитан выше, по числу путей и
колее) — точная геометрия пересекающей дороги не восстанавливается (это
разметка факта переезда на пути, а не сама проезжая часть).

## Опоры контактной сети, упрощённо (`electrified=*`)

`geometry.rail.place_catenary_poles` — только для путей с непустым и не
`no` тегом `electrified` (`contact_line`/`yes`/…). Расстановка:

- регулярный шаг `POLE_SPACING_M = 50 м` вдоль оси (типовое значение для
  прямых участков — на кривых шаг меньше, здесь не учитывается);
- один борт от оси, отступ `POLE_OFFSET_FROM_AXIS_M = 3,1 м` (габарит
  приближения опор, СТН Ц-01-95, типовое значение вне кривых);
- меш — тот же `mesh_cylinder`, что и у деревьев (`ifc.assemble`),
  `POLE_HEIGHT_M = 9 м`, `POLE_RADIUS_M = 0,15 м`.

Опоры не попадают в реестр GlobalId (`register_global_ids`) — как и штрихи
разметки перекрёстков (Шаг 2.3, п. 3), несколько опор стоят на одном
исходном `way` пути, единого `osm_id -> GlobalId` для них нет.

## Сборка в IFC

Всё семейство (лента пути, платформа, переезд, опора) — `IfcBuildingElementProxy`
с `Pset_ЖД`, БЕЗ разделения на нативный/прокси класс по схеме (в отличие от
`IfcRoad`/`IfcBridge`): нативный `IfcRail` не был задействован ещё в Шаге 1.7
и это не меняется в этом проходе — ранее ошибочная строка в
`docs/data-dictionary.md` (утверждавшая `IfcRail` в IFC4.3) исправлена заодно
с этим шагом. Все объекты Шага 2.6 исключены из `roads_backbone`/
`roads_internal` (`road_network_filter`) — это не дорожная сеть, тот же приём,
что и у `rail`/`trees` (Шаг 2.4).

## Что НЕ входит в этот проход (сознательно, честно, не обещано)

- **Шпалы и рельсы индивидуальной геометрией «в ближнем кольце»** — требуют
  интеграции с кольцами LOD (Шаг 2.1: 250×250 м, версии, стыковка), которой в
  этом проходе не делалось; сейчас путь везде — один уровень детализации
  (насыпь-лента), без LOD-зависимой детализации.
- **Порталы контактной сети на многопутных участках, чередование бортов** —
  упрощённая расстановка всегда с одной стороны, без деления консоль/портал.
- **Дифференциация колеи по типу пути** (например, узкоколейный трамвай) —
  единый `DEFAULT_GAUGE_M`, если тег `gauge` отсутствует.
- Визуальная приёмка по чек-листу (критерий шага по плану) — недоступна
  AI-сессии без человека и реального пилотного участка (Шаг 0.1).
