# Ограничения: официальные зоны и расчётные зоны (Шаги 3.1-3.2)

Реализация: `geo/src/topology_geo/constraints/{store,cli,calculated}.py`,
`geo/sql/006_constraint_zones.sql`.

## Модель данных

Одна таблица `constraint_zones` на официальные (Шаг 3.1) И расчётные
(Шаг 3.2) зоны — разница только в значении `status` (`"официально"` /
`"расчётно"`, `Pset_Ограничение.Статус` по `docs/data-dictionary.md`, §1,
строка «Охранная/санитарная зона»). Поля: `zone_type` (Вид), `regime`
(Режим — текст запретов/разрешений), `registry_number` (Реестровый номер),
`document_basis` (Документ-основание), `source_name`/`data_timestamp`
(фиксация источника и даты, тот же принцип, что `osm_import_log`/
`dem_coverage`), `geom` (`MultiPolygon`, EPSG:4326).

**Версионирование** (Шаг 3.1, п. 4: «история версий, старая версия
сохраняется»): загрузка зоны с уже известным `registry_number` (текущей,
`superseded_at IS NULL`) НЕ перезаписывает строку — старая помечается
`superseded_at = now()`, новая получает `version = старая.version + 1`.
`zone_history(registry_number)` возвращает все версии, от новой к старой —
проверено реальным тестом (`test_load_zone_with_existing_registry_number_
creates_new_version_not_overwrite`), что старая версия физически остаётся
в таблице, а не перезаписывается.

Зоны БЕЗ реестрового номера (обычно расчётные, Шаг 3.2 — у расчётной зоны
нет официального реестра) версионированию не подлежат: каждая загрузка —
независимая новая строка.

## Загрузчик (Шаг 3.1, п. 1-2)

`load_zones_from_geojson(conn, feature_collection, *, source_name,
data_timestamp)` принимает стандартный `FeatureCollection` — тот же формат,
что публичная карта НСПД отдаёт по кнопке «Скачать» для выбранного слоя
(GeoJSON/KML), не придуманный для проекта. Это одновременно закрывает оба
режима загрузки из плана: «массовая выгрузка» и «файл, полученный по
запросу» (п. 2) — для загрузчика разницы нет, оба приходят одним и тем же
GeoJSON-файлом.

Для `status="официально"` `registry_number` ОБЯЗАТЕЛЕН — прямое следствие
критерия приёмки шага («все ЗОУИТ пилота из НСПД присутствуют в модели с
реестровыми номерами»): загрузка без него честно завершается `ValueError`,
а не тихой заглушкой. Для `status="расчётно"` (Шаг 3.2) реестровый номер не
требуется.

CLI: `python -m topology_geo.constraints.cli load-file zones.geojson
--source-name "НСПД, выгрузка 2026-03-01" --data-timestamp 2026-03-01`.

## Расчётные зоны (Шаг 3.2)

Та же таблица/загрузчик (`status="расчётно"`), плюс отдельный модуль правил
`constraints/calculated.py` — каждое правило со ссылкой на реальную норму
(п. 1): СЗЗ кладбищ по площади (СанПиН 2.2.1/2.1.1.1200-03), водоохранная
зона по длине реки и прибрежная защитная полоса по уклону берега (Водный
кодекс РФ, ст. 65 — это ДВЕ разные нормы с разными аргументами, не одна
таблица по длине на обе, как можно ошибочно предположить из текста плана),
охранная зона ЛЭП по напряжению (ПП РФ №160 — **переиспользует** таблицу
`geometry.power.SAFETY_ZONE_HALF_WIDTH_M_BY_VOLTAGE_KV` Шага 2.7, п. 5, не
дублирует), охранные зоны прочих сетей по типу/диаметру (представительная
таблица по СП 42.13330/СП 124.13330/ПП РФ №878, честно помечена как
упрощённая, не исчерпывающая всех классов давления/материалов).

«Расчёт только там, где официальной зоны нет» (п. 2) —
`zones_needing_calculation(conn, bbox, zone_type)`: `True`, если среди
текущих зон в `bbox` нет ни одной с `status="официально"` ЭТОГО ЖЕ
`zone_type` — уже посчитанная РАНЕЕ расчётная зона того же вида НЕ
блокирует пересчёт (только официальная), проверено тестом
(`test_zones_needing_calculation_ignores_existing_calculated_zone`).

**Честно не реализовано:** сам вызов калькуляторов не подключён к
конвейеру задачи (`jobs.steps`) — функции реально работают и протестированы
как библиотека, но автоматический проход «для каждой ЛЭП/реки/сети на
участке посчитать зону и загрузить» — отдельная интеграционная работа,
естественное место для неё — там же, где будут потребляться зоны (Шаги
3.3/3.5, см. `constraints.md` выше).

## Градрегламент и огибающая застройки (Шаг 3.3)

Реализация: `geo/src/topology_geo/constraints/{pzz,envelope}.py`,
`geo/sql/007_pzz_zones.sql`.

Территориальные зоны ПЗЗ (п. 1) — ОТДЕЛЬНАЯ таблица `pzz_zones` (не
`constraint_zones` c `zone_type="ПЗЗ"`): параметры ПЗЗ типизированы (ВРИ —
массив строк, `max_height_m`/`max_building_percent`/`setback_m` — числа),
потому что `envelope.py` их СЧИТАЕТ, не только показывает в карточке.
`find_pzz_zone_for_point(conn, lon, lat)` — зона, содержащая точку участка
(`ST_Contains`); без загруженной зоны для места — честный `None`, не
умолчание.

Огибающая (п. 2, `compute_building_envelope`) — буквально по плану:
`участок.buffer(-setback_m)`, затем `.difference(...)` по каждой запретной
зоне (`HeightLimitedZone`, геометрия уже в локальных координатах — перевод
из WGS-84 делает вызывающая сторона, как и весь остальной проект с Шага
1.4). Ограничение по высоте — `min()` по всем источникам, у которых есть
`max_height_m` (ПЗЗ и любая `HeightLimitedZone` с известной высотой —
приаэродромная территория, зона охраны ОКН): честно берётся именно
МИНИМУМ, а не только значение ПЗЗ, «источник ограничения» попадает в
карточку регламента, чтобы было видно, ЧТО именно ограничило высоту.

Карточка регламента (п. 3) — `BuildingEnvelope.regulation_card`: ВРИ,
предельная высота и её источник, % застройки, отступ, документ-основание,
площадь пятна.

Проверки нормативных расстояний (п. 4) — реализовано только противопожарное
расстояние между зданиями (`check_fire_break_m`, СП 4.13130.2013, табл. 1,
упрощённая таблица по степени огнестойкости I-II/III/IV-V, без учёта
класса конструктивной пожарной опасности). Инсоляция соседних домов
ЧЕСТНО НЕ реализована — требует модели солнца/теней, которой в проекте ещё
нет (план вводит её отдельным Шагом 4.3 «Солнце, небо, сезоны»); считать
инсоляцию раньше своей же геометрической основы означало бы либо
дублировать её здесь заранее, либо выдать формальную цифру без реальной
модели — оставлено честной зависимостью от Шага 4.3.

**Честно не реализовано:** интеграция огибающей в IFC/вьюер («объём
допустимой застройки в IFC и во вьюере», Результат шага) — `envelope.py`
считает реальную 2D/высотную огибающую и протестирован, но экструзия в
IFC-меш и подключение к `jobs.steps`/вьюеру не сделаны в этом проходе (та
же причина, что у Шага 3.1/3.2 — естественное место для интеграции всех
трёх слоёв ограничений/ПЗЗ/огибающей в модель — Шаги 3.6-3.9, где впервые
появляется понятие «посадка ЖК на участок», которого раньше в проекте не
было: все задачи Этапов 1-2 оперируют круглой зоной радиуса, не полигоном
конкретного участка).

## Честно: что не реализовано (Шаг 3.1)

- **Прямая интеграция с НСПД/ИСОГД** — оба портала реально проверены на
  доступность из этой среды (`curl https://nspd.gov.ru`,
  `curl https://pkk.rosreestr.ru` — `Connection timed out` за 8 с, оба
  раза, без ответа прокси-статуса вовсе, в отличие от специфичного
  `ws_closed_mid_exchange` у Overpass в Шаге 2.12) — та же категория
  сетевого ограничения этой песочницы, что Geofabrik/Overpass/TessaDEM.
  Загрузчик параметризован по входному GeoJSON и не завязан на конкретный
  источник — заработает с реальной выгрузкой НСПД без изменений там, где
  есть сеть.
- **Расчётные правила Шага 3.2** (СЗЗ кладбищ по площади, водоохранные зоны
  по длине реки, охранные зоны ЛЭП по напряжению и т.д.) — сама ТАБЛИЦА и
  ЗАГРУЗЧИК готовы принять такие зоны (`status="расчётно"`), но модуль,
  который САМ СЧИТАЕТ геометрию по норме — отдельная задача Шага 3.2, не
  реализован в этом проходе (см. задачу Шага 3.2).
- **Полуавтоматический режим «по кадастровым номерам участка и соседей»**
  (Шаг 3.1, п. 2, второй вариант) — требует того же недоступного live-API
  Росреестра; режим «загрузка файлом» реализован полностью.
- **Интеграция в IFC-пайплайн** (`constraints.ifc`, федеративный файл по
  `docs/data-dictionary.md` §4) — таблица и загрузчик — независимый слой
  данных, не подключены к `jobs.steps.assemble_ifc`/вьюеру в этом проходе;
  Шаги 3.3 (огибающая застройки) и 3.5 (клик-запрос) — там, где эти зоны
  реально ПОТРЕБЛЯЮТСЯ моделью, и куда естественно ляжет эта интеграция.
