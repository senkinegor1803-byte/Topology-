# Регламент эксплуатации и поддержки (Шаг 5.4)

Буквально по плану (Шаг 5.4): расписание обновлений данных, порядок
обработки обращений, план развития. Это организационный документ, не код —
но расписания ниже опираются на реально реализованные в проекте механизмы
версионирования источников (Шаги 1.1, 1.2, 3.1, 3.10), а не на
предположения о том, что «неплохо бы» их иметь.

## 1. Расписание обновления данных

| Источник | Периодичность (по плану) | Механизм версионирования в коде | Где |
| --- | --- | --- | --- |
| OSM | Еженедельно | `osm_import_log`: `source_name` + `data_timestamp` (дата актуальности выгрузки источника, отдельно от `imported_at` — момента запуска импорта) + минутные диффы через `osm2pgsql-replication` между полными обновлениями. | `docs/osm-import.md`, `geo/src/topology_geo/osm/import_log.py` |
| Официальные ограничения (ЗОУИТ/ПЗЗ/красные линии/ОКН/ООПТ) | Ежемесячно и по событию (публикация новых актов) | `constraint_zones`: `source_name` + `data_timestamp` + `version` + `superseded_at` — полная история версий, старая запись не удаляется, а помечается замещённой. | `docs/constraints.md`, `geo/src/topology_geo/constraints/store.py` |
| Рельеф (DEM/топосъёмка) | По мере поступления новых данных (топосъёмка пилота, обновления TessaDEM) | `dem_coverage`: `source_name` + `data_timestamp`, индекс покрытия в PostGIS. | `docs/relief.md`, `geo/src/topology_geo/relief/coverage.py` |
| Справочник РСО (организации, зоны обслуживания) | Раз в квартал | `rso_directory.verified_at` — дата последней проверки актуальности записи. **Честно:** это только отметка свежести, не полная история версий, как у `constraint_zones` (нет `superseded_at`/`version`) — при квартальной проверке старую запись стоит обновлять на месте либо переносить в отдельный архив вручную, автоматической версионируемой замены пока нет. | `docs/rso.md`, `geo/src/topology_geo/rso/directory.py` |

**Порядок обновления OSM** (еженедельно): запустить скрипт полного импорта
(`geo/scripts/*.sh`, см. `docs/osm-import.md`) с новой выгрузкой
Geofabrik/Overpass, `data_timestamp` — дата выгрузки источника (не дата
запуска скрипта). Между полными обновлениями — минутные диффы
(`osm2pgsql-replication`) можно применять по расписанию (cron/systemd timer)
без ручного вмешательства.

**Порядок обновления ограничений** (ежемесячно + по событию): при
публикации нового акта (изменение ЗОУИТ/ПЗЗ и т. п.) — новая запись в
`constraint_zones` с новым `version`, старая помечается `superseded_at`
(история не теряется, отчёты по прошлым посадкам ЖК остаются
воспроизводимыми на данных своего времени).

**Порядок обновления справочника РСО** (раз в квартал): для каждой
организации — проверить контакты, канал подачи заявки и зону обслуживания,
обновить `verified_at`. Практика показывает, что реквизиты РСО меняются
реже ограничений — квартальная периодичность (как и в плане) избыточна не
будет, но и более редкая проверка рискует устаревшими контактами в пакете
ТУ (Шаг 3.11).

## 2. Порядок обработки обращений пользователей и ошибок в данных

1. **Канал обращения**: пользователь сообщает об ошибке через
   API-интеграцию своей организации (вебхуки/API-ключи, Шаг 4.11) или
   напрямую администратору/OPS — отдельной формы обратной связи внутри
   продукта в этом проходе не построено (см. `docs/user-guide.md`, раздел
   10).
2. **Классификация**:
   - *Ошибка в данных источника* (неверный атрибут OSM, устаревшие
     ограничения, неверные контакты РСО) — не патчится точечно в БД
     проекта (иначе следующий импорт источника сотрёт правку без следа);
     исправляется в первоисточнике (OSM — через обычный процесс OSM,
     официальные данные — запрос повторной выгрузки у поставщика) и
     проверяется при следующем плановом обновлении по расписанию из
     раздела 1.
   - *Ошибка конвейера* (упавший шаг задачи, неверная геометрия,
     некорректный IFC) — воспроизводится на той же задаче
     (`GET /jobs/{id}` содержит журнал шагов с ошибкой) и заводится как
     дефект в трекере разработки; критичные — исправляются вне очереди,
     некритичные — в порядке общего бэклога.
   - *Организационное обращение* (доступ, роль, право на закрытый контур)
     — обрабатывается администратором через `PATCH /auth/users/{id}/role`
     (см. `docs/admin-guide.md`, раздел 5).
3. **Приоритеты**: критичное (сервис недоступен, утечка закрытых данных,
   неверный результат, затрагивающий уже поданные ТУ) — реагирование
   в течение рабочего дня; некритичное (косметическое, единичный
   устаревший атрибут) — в порядке общего бэклога.
4. **Обратная связь**: после исправления — уведомление обратившемуся тем
   же каналом, которым пришло обращение.

## 3. План развития

По плану проекта, три направления после ввода в эксплуатацию:

1. **Подключение других городов Пермского края** — большая часть
   конвейера уже параметризована по МСК-59 и зонам (`coords.py`,
   `pick_msk59_zone`), а не жёстко привязана к Перми; для нового города
   потребуются: своя выгрузка OSM/DEM/ограничений для его территории,
   проверка попадания в существующие или новые зоны МСК, наполнение
   `rso_directory` организациями этого города.
2. **Новые слои данных** — расширение словаря данных
   (`docs/data-dictionary.md`) и OSM flex-стиля (`geo/osm2pgsql/style.lua`)
   под новые типы объектов по мере запросов от пользователей.
3. **Доработки по замечаниям опытной эксплуатации** (Шаг 5.2) — журнал
   замечаний с приоритетами из отчёта опытной эксплуатации становится
   входом в обычный бэклог разработки; сам отчёт и журнал появятся только
   после реального пилота (Шаг 0.1, честный отказ — см.
   `docs/dev-tree.md`, строка 5.2).

## 4. Критерий шага (честно)

План требует «месяц работы без ручного вмешательства в конвейер» — этот
критерий проверяется временем, а не кодом или документом, и требует
реальной эксплуатации на реальных данных (которой ещё не было — Шаг 0.1).
Этот регламент задаёт процесс, соблюдение которого можно будет
зафиксировать только после месяца реальной работы.
