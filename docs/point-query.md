# Карточки объектов и точечный запрос (Шаг 3.5)

Реализация: `geo/src/topology_geo/query/{point_query,excel_export}.py`,
`geo/src/topology_geo/constraints/store.py::{find_zones_near_point,
search_zones}`.

## Клик по точке (п. 2)

`query_point(conn, lon, lat, max_distance_m=500.0)` — реальный
метрический запрос PostGIS (`geom::geography`, не градусы — на широте
Перми 1° долготы и 1° широты — разное число метров, сравнение в градусах
было бы неверным), возвращает зоны В ПРЕДЕЛАХ расстояния, отсортированные
по возрастанию (ближайшая первая), плюс территориальную зону ПЗЗ,
содержащую точку. Критерий шага («где проходит ВЛ и её охранная зона» — 2
клика) реально проверен тестом: один вызов `query_point` (= один клик по
карте, второй клик — открыть уже готовую карточку) находит охранную зону
ЛЭП со статусом и напряжением из `regime`.

Панель свойств с группировкой (п. 1: «основное, источник, ограничения,
ссылки») — `PointQueryCard.to_grouped_dict()` уже раскладывает поля по
этим четырём группам буквально по тексту плана; фронтенду остаётся
отрисовать структуру, не придумывать группировку заново.

**Честно не включено в карточку:** ближайшие ПОДЗЕМНЫЕ сети (`networks.
dxf_import`, Шаг 3.4) и отметка рельефа — обе требуют доступа к объектному
хранилищу (DXF-импорт не персистится в PostGIS, только парсится в память;
растр рельефа читается из Storage), которого у `query_point` сознательно
нет (принимает только `conn`, как весь остальной `constraints`-слой) —
естественное место для сборки полной карточки — API-слой (Шаг 1.3,
`api/app.py`), где `conn` И `storage` уже оба доступны вместе.

## Фильтры/поиск + выгрузка в Excel (п. 3)

`constraints.store.search_zones(conn, *, zone_type=, status=,
registry_number_contains=)` — фильтр по типу/статусу/подстроке реестрового
номера. Фильтрация «по напряжению, диаметру» из текста плана — ЧЕСТНО НЕ
реализована: оба параметра относятся к конкретным объектам (ЛЭП, сети), не
к обобщённой зоне ограничения — `constraint_zones.regime` хранит их
свободным текстом, не структурированным числом (в Шаге 3.1 не было
причины заводить для них отдельные типизированные столбцы — универсальная
таблица зон ограничений разного вида, не таблица ЛЭП/сетей).

`query.excel_export.zones_to_excel(zones) -> bytes` — реальный `.xlsx`
через `openpyxl` (новая зависимость — план буквально называет Excel, не
просто табличный CSV), собран в памяти (тот же приём, что `export.dxf.
build_dxf`, Шаг 2.10) — вызывающая сторона решает, куда положить байты.

## Честно не реализовано

- «Подписи линий и зон прямо на модели» (п. 4) — фронтенд-функция
  (текстовые метки в 3D-сцене вьюера), не реализована в этом проходе;
  вьюер уже показывает атрибуты по клику через панель свойств (Шаг 1.9) и
  всплывающее окно на карте (Шаг 2.12) — постоянные подписи НА самой
  геометрии (не по клику) требуют отдельной работы с `THREE.Sprite`/
  HTML-оверлеями, не сделано.
- Ближайшие подземные сети и отметка рельефа в карточке — см. выше,
  зависит от подключения Storage на уровне API, не самого запроса.
- Фильтрация по напряжению/диаметру — см. выше, требует структурированных
  столбцов, которых нет в универсальной таблице зон.
