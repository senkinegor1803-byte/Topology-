# Справочник РСО и определение владельцев сетей (Шаг 3.10)

Реализация: `geo/src/topology_geo/rso/directory.py`, `geo/sql/008_rso_directory.sql`.

## Справочник (п. 1)

Таблица `rso_directory` — поля буквально по действию плана: вид сети
(`network_type`, тот же словарь К/В/Т/Г/Кл, что `networks.dxf_import`
Шага 3.4), зона деятельности (`service_area`, геометрия — организация
может обслуживать не весь город), официальные контакты, канал подачи
заявки (`application_channel` — `письмо`/`личный кабинет`/`Госуслуги`/
`МФЦ`, ограничено `CHECK`, а не свободный текст — план перечисляет ровно
эти четыре канала), дата проверки (`verified_at`).

## Каскад определения владельца (п. 2)

`resolve_network_owner(conn, network_type, lon, lat, *, osm_operator=None)`
— план описывает каскад из ЧЕТЫРЁХ шагов: `operator` в OSM → правообладатель
по НСПД/ЕГРН → зоны ЕТО/гарантирующих организаций по схемам тепло-/
водоснабжения → справочник. Честно реализованы ПЕРВЫЙ (тег OSM — модуль
его не запрашивает сам, принимает параметром, так как выборка тегов уже
делается Шагом 1.4) и ПОСЛЕДНИЙ (справочник, `find_rso_for_point` по
`ST_Contains(service_area, точка)`) шаги каскада; средние два (НСПД/ЕГРН,
муниципальные схемы тепло-/водоснабжения) пропущены — оба требуют живых
внешних порталов, недоступных из этой сетевой среды (тот же класс
ограничения, что Geofabrik/Overpass/НСПД в Шагах 2.12/3.1). Функция НЕ
подделывает эти два шага молчаливым пропуском — `OwnerResolution.source`
честно называется `"OSM operator"` или `"справочник РСО"`, никогда не
`"НСПД"`/`"схема водоснабжения"`, которые не выполнялись.

## Непредставленные случаи (п. 3)

Если ни тег OSM, ни справочник не дали ответа — `OwnerResolution.source
== "требует уточнения"` (буквально статус из плана), `owner_name = None`
— честный тупик каскада, не выдуманный владелец.

7 новых тестов (`test_rso_directory.py` — 6, `test_rso_sql_migrations.py`
— 1).

## Шаблоны и формирование запросов ТУ (Шаг 3.11)

`rso/tu_request.py` (новые зависимости `python-docx`, переиспользует
регистрацию кириллического шрифта из `siting.pdf_report`, не дублирует).

Поля заявки (п. 1) — `TuRequestFields` (заявитель/кадастровый номер/
адрес/назначение объекта/нагрузки по типу сети/сроки — буквально по
плану). Заполнение DOCX (п. 2) — `fill_docx_template`: реальная
особенность `python-docx`, воспроизведённая тестом явно, а не
предполагаемая — плейсхолдер может физически разорваться МЕЖДУ
несколькими `run` одного параграфа (Word хранит форматирование
фрагментами), поэтому текст параграфа сначала собирается целиком, потом
заменяется. Настоящего фирменного шаблона РСО в этой среде нет — план сам
предполагает шаблон от пользователя («после получения форм от
пользователя», срок шага) — `build_default_template` строит минимальный,
но настоящий `.docx` с теми же плейсхолдерами для примера/тестов, не
выдаёт себя за реальный бланк. Выкопировка PDF (п. 2, приложение) —
`build_site_excerpt_pdf`.

Комплект для порталов (п. 3) — `build_tu_request_package`: zip с
`request.docx`+`attachment.pdf`+`fields.json` (структурированные поля —
для ручного переноса в формы порталов без загрузки файла целиком), тот же
приём упаковки, что `jobs.steps.package_outputs` (Шаг 2.10).

Отправка только после проверки человеком (п. 4) — реализовано ОТСУТСТВИЕМ
функции автоотправки: модуль строит файлы и ничего никуда не отправляет
— ни одной интеграции с порталами РСО в проекте нет.

5 новых тестов (`test_rso_tu_request.py`), включая явное воспроизведение
разрыва плейсхолдера между `run`.

**Честно не реализовано:** реальный фирменный шаблон РСО (нужен от
пользователя); критерий шага («пакет принят РП без правок в данных») не
проверен без реального пилота (Шаг 0.1) и реальных форм пользователя.

## Реестр запросов и привязка ТУ (Шаг 3.12)

`rso/tu_registry.py`, `geo/sql/009_tu_requests.sql`.

Реестр (п. 1) — таблица `tu_requests` (организация/дата/канал/входящий
номер/срок/статус, буквально по плану). Срок ответа считается сразу при
регистрации (`sent_at + 30 дней` по умолчанию — реальная норма ГрК РФ,
ст. 48, ч. 7: «срок предоставления технических условий... не может
превышать 30 дней», не произвольное число; вызывающая сторона может
передать другой срок для конкретной сети/организации) — единый источник
правды и для реестра, и для напоминаний, не отдельно хранимая копия.

Напоминания о сроках (п. 1) — `overdue_requests` находит запросы с
истёкшим сроком и статусом `"отправлен"` (ответ так и не получен);
`mark_overdue` явно переводит их в `"просрочен"` — ОТДЕЛЬНЫМ действием, не
автоматически при каждом чтении реестра (иначе один вызов «посмотреть
просроченные» тихо менял бы состояние базы — не то поведение, которого
ждут от функции чтения).

Загрузка полученных ТУ + привязка точки подключения (п. 1, последняя
часть) — `record_response`: входящий номер, точка подключения (геометрия)
и параметры из ТУ пишутся в ту же таблицу, откуда модель сможет их прочитать
— один источник в PostGIS, тот же принцип, что и у остальных геослоёв
проекта (Шаг 3.1/3.10).

7 новых тестов (`test_rso_tu_registry.py` — 6, `test_tu_requests_sql_
migrations.py` — 1).

**Честно не реализовано:** отображение точки подключения НА СЕТИ В МОДЕЛИ
(последняя часть действия «отображаются на сети в модели») — данные для
этого уже есть в таблице (`connection_point`/`connection_params`), но
подключение к вьюеру/API не сделано в этом проходе, естественное
продолжение — там же, где остальные геослои Этапа 3 подключаются к модели
(ещё не сделано ни для одного из них). Критерий шага («полный цикл
запрос→ответ→точка подключения в модели пройден на пилоте») не проверен
без реального пилота (Шаг 0.1).

## Честно не реализовано

- Средние два шага каскада (НСПД/ЕГРН, схемы тепло-/водоснабжения) — см.
  выше, требуют внешних порталов, недоступных в этой сетевой среде.
- Критерий шага («на пилоте владельцы совпадают с проверенными вручную»)
  не проверен — нужен реальный пилотный участок (Шаг 0.1).
