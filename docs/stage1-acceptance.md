# Протокол приёмки Этапа 1 (Шаг 1.10)

Живой документ: фиксирует, что из критериев приёмки Этапа 1 (раздел 14 ТЗ,
`docs/plan.md`) проверено автоматически и чем именно, а что остаётся
человеку. Источник истины по факту — тесты
`geo/tests/test_stage1_acceptance.py`; этот документ описывает методику и
приводит один опорный прогон как иллюстрацию, а не как гарантированное
число (реальное время зависит от машины/объёма данных).

## Методика (Шаг 1.10, п. 1-2)

Конвейер (Шаги 1.1-1.9: импорт OSM → рельеф → выборка/нормализация → TIN →
здания/дороги/вода/рельсы/деревья → сборка IFC (обе схемы) → GLB) прогоняется
целиком, на реальных сервисах (`osm2pgsql`+PostGIS, Redis, Celery в eager-
режиме — то же, что и в `test_api.py::test_full_happy_path_...`), для трёх
профилей участка, чтобы задеть разные комбинации типов объектов и путей
нормализации:

| Профиль | Состав | Что именно проверяет |
| --- | --- | --- |
| Центр | 3 многоэтажных здания (высота из `height`/`building:levels`/дефолта — все три пути формулы §2.5), магистраль 4 полосы + второстепенная | Плотная застройка, разные источники высоты в одном участке |
| Спальный район | 2 дома по 9 этажей, дворовые проезды (`residential`+`service`), зелёный двор (`landuse=grass`), пруд (`natural=water`) | Вода (уровень уреза), внутриквартальная сеть, зелень |
| Частный сектор | 3 маленьких дома (`building=house`, без height/levels — только дефолт по типу), грунтовая дорога (`surface=unpaved`) | Полностью дефолтная высота, немощёная дорога |

Для каждого профиля: задача ставится через `POST /jobs` (радиус 500 м, как в
MVP Этапа 1), опрашивается до `done`, из журнала (`GET /jobs/{id}`)
считывается время каждого шага (`started_at`/`finished_at`), из
`GET /models/{id}/files` проверяется, что `site.ifc` (обе схемы) и `site.glb`
реально скачиваемы.

### Опорный прогон (пример, не гарантия)

```
[центр]            9.25 с   select_osm 0.05 · prepare_relief 0.22 · select_and_normalize 6.08 · assemble_ifc 1.54 · convert_to_glb 0.96
[спальный_район]   3.55 с   select_osm 0.02 · prepare_relief 0.17 · select_and_normalize 0.08 · assemble_ifc 1.61 · convert_to_glb 1.54
[частный_сектор]   1.60 с   select_osm 0.02 · prepare_relief 0.10 · select_and_normalize 0.05 · assemble_ifc 0.71 · convert_to_glb 0.59
```

(`select_and_normalize` у профиля «центр» дороже из-за холодного старта
GDAL/pyogrio в первом тесте процесса — не из-за размера данных: профили
на порядок меньше реального участка 500 м с настоящей плотностью OSM.)

## Геометрическая точность (раздел 14 ТЗ: «расхождение с OSM ≤ 0,5 м»)

Не повторная проверка координатного пересчёта (это уже 61 тест Шага 1.4 и
тесты Шага 0.4) — `test_building_footprint_survives_ifc_export_within_half_a_meter`
проверяет, что сборка IFC (Шаг 1.8: репарация контура, `mapbox_earcut`,
экструзия) НЕ вносит собственного смещения между нормализованными локальными
координатами объекта (то, что реально идёт на сервер, Шаг 1.4) и контуром,
экспортированным в `site.ifc` (считан обратно через `ifcopenshell.geom`,
сравнён по Хаусдорфу с исходным контуром). На опорном прогоне отклонение —
`0.000000 м` (пересборка мешей не искажает координаты, как и ожидалось: все
преобразования между Шагом 1.4 и Шагом 1.8 — репроекция уже сделана раньше,
дальше только дедупликация/переориентация кольца и триангуляция, без сдвига
точек).

## Что подтверждено автоматически (эта сессия)

- ✅ Конвейер целиком отрабатывает без ошибок на всех трёх профилях —
  `test_pipeline_completes_for_each_site_profile[*]`.
- ✅ Время каждого шага измеряется и попадает в журнал задачи (п. 2 Шага 1.10).
- ✅ Итоговое время конвейера — на порядки меньше 5 минут на синтетических
  данных этого масштаба (регрессия против зависания, не проверка реального
  времени на пилотных объёмах).
- ✅ Плановое расхождение экспортированной геометрии от нормализованных
  локальных координат — 0 м на всех проверенных случаях (`≤ 0,5 м` с большим
  запасом).
- ✅ `site.ifc` (IFC4 и IFC4X3) проходит `ifcopenshell.validate` без замечаний
  для всех трёх профилей (наследуется из Шага 1.8, повторно задействовано
  здесь на новых данных).

## Что НЕ может подтвердить AI-сессия (п. 3-4 Шага 1.10)

- ⛔ **Открытие в Renga и Pilot-BIM** — нужно установленное ПО и человека с
  лицензией; это явно требует BIM-специалиста (роль из плана). Автоматическая
  валидация схемы (`ifcopenshell.validate`) — необходимое, но не достаточное
  условие: она не ловит, например, визуально «вывернутые» нормали стен или
  неудобную для навигации структуру дерева объектов в самой Renga.
- ⛔ **Протокол замечаний BIM-специалиста и повторная проверка** (п. 3-4) —
  по определению требует итерации с человеком; здесь фиксируется только то,
  что код готов принять такие замечания (issue/задача) и они не блокированы
  архитектурно.
- ⛔ **Критерии на реальном объёме** — «≤5 мин» и «расхождение ≤0,5 м» из
  раздела 14 ТЗ сформулированы для реального пилотного участка (Шаг 0.1) с
  плотностью объектов настоящего города, а не для синтетических профилей
  из нескольких зданий. Методика (эта секция) переносится на пилот без
  изменений, как только участок выбран — тот же тест, реальные данные вместо
  синтетических OSM-фикстур.
- ⛔ **«На телефоне» (Шаг 1.9)** — не проверялось, нет реального устройства.

## Как продолжить приёмку на реальном пилоте

1. Выбрать участок (Шаг 0.1) → получить координаты центра.
2. Прогнать `POST /jobs` с этими координатами (реальный OSM должен быть уже
   импортирован, Шаг 1.1; реальный DEM загружен, Шаг 1.2).
3. Замерить те же метрики, что в опорном прогоне выше (журнал задачи это
   делает автоматически).
4. Передать `site.ifc` BIM-специалисту для открытия в Renga/Pilot-BIM,
   зафиксировать замечания, завести их как задачи, поправить, повторить.
5. Обновить этот документ реальными числами и результатом ручной проверки —
   тогда, и только тогда, Этап 1 закрывается по критерию плана полностью.
